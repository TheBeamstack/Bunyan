# `P4.5_interaction_model_design.md` — The Interaction Model

**Phase:** P4.5 (the tool/interaction layer — the first-class layer D47 found missing).
**Driver:** Amer (the tool layer, the browser) · Architect (type semantics, the reservations, the sign-off) ·
Zayd (only if a snap needs a kernel op that does not already exist — the design below says it does not).
**Status:** DESIGN-FIRST. This document is the deliverable. Its open questions (§12) go to the owner; the
build does not start until they are ruled. **Read `review_P4.md` §1 (the source of D47) and
`v1.0.0_imp_plan.md` "P4.5" first — this doc is the design those steps asked for, grounded against the real
`apps/web` code as it stands at Entry 65.**

**What this is a design of, and what it must not become.** The interaction model is a **UI state machine
upstream of the one Command layer** — never a second command layer, never a holder of a `KernelClient`,
never a writer of model state. Every gesture ends in **exactly one `Command` dispatch**, so the human and
the agent keep sharing one door (D19). What the tool layer changes is not the door; it is **what the door's
arguments have to look like** — and those arguments (`Command.argsSchema`, `Element.placement`,
`UndoableEdit`) freeze at **P5 step 6**. That is the whole reason this phase sits _before_ the freeze:
§9 and §10 are the two pre-freeze obligations (freeze-gate rows ⓑ and ⓘ), and they are cheap only until
the owner freezes.

---

## §0 — The one-sentence diagnosis (D47), and why it is a contract problem

`argsSchema` is a **machine-readable contract for an agent**, and the app renders it as a **UI form for a
human** (`SchemaForm.tsx`). To place a window today a human must hand-type a persistent-naming derivation
token (`wall-01J8Z3K7Q2….finish.interior/face/y-min#0`) into a text box — the exact string D44 says must
never be shown to a user as a name. In every real BIM tool a ribbon button does **not** open a form; it
**activates a tool**, and the tool collects its own arguments _from the viewport_: click, snap, rubber-band,
type a number to override, commit. `D21` ("one schema, three consumers") is right for the property panel and
right for the agent tool list; for the **ribbon** it silently substituted a _form_ for a _tool_. This phase
supplies the missing consumer — the tool — without weakening the door it feeds.

**The ground truth this design is built on (verified against the code at Entry 65):**

- **No command moves an element.** The 39 registered commands are all CRUD; `placement` is set at
  `core.createElement` and can never be changed (`commands.ts`). `core.setPlacement`/`move`/`rotate`/
  `copy`/`array` **do not exist**. (§9.)
- **The renderer already retains everything a snap needs.** Each `DrawnPart` in `Viewport` holds the full
  `MeshBuffers` — `positions`, `edgePositions`, and the `provenance` (`refs` / `triangleToRef` / `edges`)
  keyed by stable `nodeId` (`Viewport.ts:55`, `mesh.ts:41`). Picking is already a pure triangle→`SubShapeRef`
  resolution through that provenance (`pick.ts`, `Viewport.pick`). **Snapping is the same substrate, one
  step further: edge endpoints and face frames instead of hit triangles.**
- **The kernel already has the exact spatial ops** — `distance`, `bounds`, `classifyPoint`, `faceFrame` are
  live and tested — but **no seam lets the UI reach them.** The three existing seams each refuse it by
  design: the agent surface returns semantics not geometry; `RenderGateway` exposes `tessellate` and nothing
  else; `GeometryGateway` is the document's, not the UI's. (§4.)
- **The dispatch discipline for a drag already exists.** `createLatestRunner` (`runner.ts`) is single-flight,
  trailing-latest — a 60 fps drag collapses to "run this frame, then the latest frame"; and the kernel's
  `coalesceKey` / `SUPERSEDED` path already makes a superseded rebuild the _expected_ outcome of an
  intermediate frame. The tool layer schedules **previews** on the same runner and **commits** exactly once
  at the end.

## §1 — Domain rule 17 (proposed) — the invariant this phase adds

> **Domain rule 17: A TOOL COLLECTS INPUT; ONLY A COMMAND CHANGES THE MODEL.** A tool is a UI state machine
> that gathers arguments — a point, a face, a length — and **commits exactly one `Command`**. It is never a
> second command layer, it never touches the kernel, and **an in-progress tool interaction is not model
> state**: nothing half-drawn is ever in the document, so a refresh, an undo, a save, or an agent query can
> never observe it. _(This keeps domain rule 9 intact — there is still exactly one command layer, and a tool
> is strictly upstream of it.)_

This belongs in `core_logic.md` §8 because the invariant is a **domain** invariant, not a UI convenience: it
is what guarantees the tool layer cannot smuggle in a private authoring path (the P4 equivalence test, now
run against a _tool-authored_ edit, is the machine-check of it — §11). **Proposed as an owner ruling
(Q1).** Adding it renumbers nothing; it is rule 17 after the existing sixteen.

⚠ There is already a documentation-side "rule 17" referenced in `schedule.ts` ("stored-vs-derived is legible
from the file a type is in"). That is a _code-comment_ convention, not a numbered `core_logic.md` §8 rule.
**Confirm the numbering with the owner (Q1)** so the domain rule list and the comment convention do not
collide — if they would, this becomes domain rule 19 (the next free number after the sixteen model rules
plus any the docs have since added).

## §2 — The tool state machine

A tool is a small, explicit state machine with **no persistence** and **no document reads that mutate**:

```
  activate ──► collect(input₁ … inputₙ) ──► preview (every frame) ──► commit ONE Command ──► deactivate
      ▲               │                                                                          │
      └───────────────┴──────────────────── Esc: cancel, leave NO trace ◄────────────────────────┘
```

- **`activate`** — a ribbon button (or a keyboard shortcut) puts a tool into the single active slot. Exactly
  one tool is active at a time; activating another cancels the first with no trace. The default tool is
  **Select** (§8).
- **`collect(n inputs)`** — the tool declares an ordered list of inputs it needs (a start point, an end
  point; or a host face, then a UV offset). Each input is satisfied by a **click that has been resolved
  through the snap seam** (§4) or by **numeric entry** (§6) that overrides the pointed value. The tool holds
  its collected inputs in **its own local state**, never in the scene.
- **`preview`** — after each input and on every pointer-move frame, the tool draws a **cheap local
  approximation** of the result (§5). The preview is scheduled on the existing `LatestRunner` so it inherits
  the trailing-latest discipline; it is **never** the real command and **never** truth.
- **`commit`** — when the last input is satisfied, the tool builds the `Command` args from its collected
  inputs and dispatches **exactly one** `Command` through the existing `Dispatch` (`runner.ts`). The returned
  `UndoableEdit` is the only thing that ever reaches the document. On failure, the existing error banner
  shows it and the tool returns to its start state (nothing was committed — D42).
- **`Esc`** — cancels at any collection step and leaves **no trace**; `Enter` commits early where a tool
  allows it (e.g. a polyline wall). Numbers typed at any point open the numeric-entry field (§6).

**A tool is a registry entry, like everything else in this product.** A new type ships its tool the way it
ships its `argsSchema` and its `buildGeometry` — this is D21's spirit applied to _input_ rather than to
forms. Proposed shape (an **app-layer** registry — it touches no frozen contract, so it is additive and
below the freeze):

```ts
interface Tool {
  readonly id: string; // 'tool.wall', 'tool.opening', 'tool.select', 'tool.move'
  readonly label: string; // ribbon caption
  readonly inputs: readonly InputSpec[]; // ordered; each names what it snaps to + whether numeric entry applies
  begin(ctx: ToolContext): ToolSession; // pure factory; ctx exposes the snap seam + Dispatch + a preview sink
}
```

⚠ **The tool registry is `apps/web`-only and must stay there.** It is emphatically **not** a `scene.json`
collection, not a document registry, and not part of any frozen contract — a tool is disposable UI, and
putting it below the freeze would be the exact D47 mistake in reverse. (The **agent** never needs a tool; it
calls the `Command` directly. Tools exist only because a _human_ points instead of typing.)

## §3 — Where the tool layer lives (the app architecture)

```
  Ribbon button / shortcut ─► ToolController (the single active-tool slot, keyboard, numeric entry)
                                    │  reads →  SnapGateway (§4, read-only)          ← retained MeshBuffers + kernel query ops
                                    │  draws →  PreviewLayer (§5, three.js overlay)  ← never the document
                                    └─ commits → Dispatch (runner.ts) ─► DocumentContext ─► kernel
```

- `ToolController` is a new `apps/web/src/tool/` module. It owns the active tool, the keyboard handlers
  (there is currently **not one `keydown` handler in the entire app** — §7), and the numeric-entry field.
- The `PreviewLayer` is a three.js overlay group inside `Viewport` (a sibling of the two `PartBatch`
  objects), drawn in a distinct material and **excluded from picking and from the snap index** — a preview is
  never a snap target.
- Nothing here holds a `KernelClient`. The `SnapGateway` (§4) is read-only and mints no identity, so
  `d19-boundary.test.ts` stays green (§11).

## §4 — THE SPATIAL-QUERY SEAM (the real work of this phase)

**No actor in the app can currently ask a geometric question in world space, and every snap is one.** This
seam is the missing one the plan names. It is a **read-only** seam: it authors nothing, owns nothing, and
mints no identity — the same argument that legitimised `RenderGateway`, so it is **not** a D19 violation.

### 4.1 The two-tier design (recommended, and written down on purpose)

> **Tier 1 — the browser-side snap index (per-frame, cheap, approximate).** Built from the geometry the
> viewport already retains: each `DrawnPart`'s `edgePositions` (edge polyline vertices ⇒ **endpoints** and
> **midpoints**), `positions`/`provenance` (**face** hits, already resolved by `pick.ts`), and the scene's
> grids and levels (**grid intersections**, **level planes** — from `scene.json`, no kernel). A uniform
> spatial hash over these candidate points, rebuilt incrementally as `setScene` installs/removes parts
> (the same `nodeId`-keyed lifecycle the `#drawn` map already follows). A snap query is then a screen-space
> nearest-candidate lookup within a pixel tolerance — fast enough for 60 fps at the 10k-element target.
>
> **Tier 2 — the kernel's exact ops as the _confirming_ fallback.** `distance`, `classifyPoint`, `faceFrame`,
> `bounds` are live and exact. They are used **only** at commit boundaries and for the handful of snaps the
> mesh cannot answer honestly (a true edge–edge intersection point, an exact perpendicular foot on a curved
> face). They are **never** on the per-frame path (a one-wall `dryRun` rebuild is ~100 ms — §5 — and a
> kernel round-trip per snap is the same order; both are far too slow at 60 fps).

**Why this is written down and not left to the implementer:** _"the snap that lied"_ — a snap that reports a
point a millimetre off the true geometry because the mesh is a chord approximation — is a class of bug that
is very hard to see and corrupts a model silently (§4.4). Recording that **Tier 1 is approximate and Tier 2
is truth**, and that a _committed_ coordinate that matters is always confirmed against Tier 2, is the
guard-rail. This mirrors the preview/`dryRun` distinction in §5 exactly.

### 4.2 The seam's shape (app-layer, read-only)

```ts
interface SnapGateway {
  /** Nearest snap candidate to a screen ray, within `pixelTolerance`. Pure Tier-1; no kernel. */
  snap(ray: ScreenRay, filter: SnapKinds, pixelTolerance: number): SnapHit | null;
  /** Exact confirmation of a world point against real geometry (Tier-2). Used at commit, not per frame. */
  confirm(point: Vec3, against: SubShapeRef): Promise<Vec3>; // wraps kernel distance/faceFrame/classifyPoint
}
interface SnapHit {
  readonly point: Vec3; // world mm
  readonly kind: SnapKind; // 'endpoint' | 'midpoint' | 'intersection' | 'face' | 'grid' | 'perpendicular' | 'extension' | 'vertex'
  readonly ref?: SubShapeRef; // present when the snap is ON a named sub-shape (a face/edge/vertex) — the pick path
  readonly hostElementId?: ElementId; // present when the snap is on an element — feeds hosting args
}
```

⚠ `SnapHit.ref` is where **face-click hosting** (the exit criterion "a window is placed by CLICKING A FACE,
and no human types a derivation token") is produced: a face snap carries the `SubShapeRef` `pick.ts` already
resolves, so the tool hands `{ hostId, hostRef }` to `core.createElement` without a human ever seeing the
token. This is the first end-to-end proof of P2's persistent naming in the hands of a user, not a test.

### 4.3 Snap kinds, inference, and alignment guides

- **Snap kinds** (Tier-1 candidates): endpoint, midpoint, face, grid intersection, level plane, and the
  **derived** kinds — perpendicular foot, extension (along an existing edge's line), and intersection of two
  candidate lines. `vertex` is reserved in the `SubShapeRef` role grammar (D54a) but the kernel does not
  export vertices yet; a vertex snap in v1.0.0 is served by Tier-1 (an edge polyline endpoint), and upgrades
  to an exact kernel vertex when a v1.0.x consumer needs it — no seam change.
- **Snap priority** (when several candidates fall inside the pixel tolerance): explicit vertex/endpoint >
  intersection > midpoint > grid > perpendicular/extension > face-plane > free point. **This ordering is a
  proposed default (Q3)** — it is the ArchiCAD/Revit convention, but the owner may want a different tie-break.
- **Inference / alignment guides** are a _rendering_ of Tier-1 candidates: when the cursor is aligned
  (horizontally/vertically/on-axis) with a live reference point, draw a dashed guide line and snap to it.
  These are pure overlay geometry in the `PreviewLayer` — no model state, no contract.

### 4.4 D19 and the "snap that lied" guard (the standing constraints in force)

- **D19 stays a machine check.** `SnapGateway` holds no `KernelClient`; its Tier-2 `confirm` goes through the
  same narrow read-only kernel view `RenderGateway` uses (derived in `bootstrap.ts`, the one allowed holder).
  It exposes `distance`/`classifyPoint`/`faceFrame`, never `makeBox`/`boolean`/anything that authors.
- **Approximate never commits silently.** A snapped coordinate that becomes a _committed argument_ and whose
  exactness matters (a baseline endpoint that must lie exactly on a grid; a host UV that must lie on a real
  face) is resolved to the **exact** value at commit — either from the snap's own exact source (a grid
  intersection is exact from `scene.json`; a face UV is exact from `faceFrame`) or via Tier-2 `confirm`.
  **The mesh's approximate point is used to _choose_ the target, never to _record_ the coordinate.** This is
  the measured-not-asserted discipline (§1b) applied to the pointing device.

## §5 — Preview, hover, gizmo — and the trap inside the preview

- **The preview is a cheap local approximation drawn by the renderer, and it is NEVER truth.** D42's
  universal `dryRun` is the _semantically_ perfect preview (the real command, the real kernel, result
  discarded) but it is **~100 ms per frame** (measured, a one-wall rebuild) and cannot drive a 60 fps rubber
  band. So the rubber-band wall, the ghost window, the move offset are all **overlay geometry** the tool
  draws directly (a line, a box, a translated clone of the retained mesh). **Write this distinction down or
  someone will make the preview authoritative and re-introduce the half-committed state D42 abolished.**
- **`dryRun` backs a _commit-time_ confirmation, not the per-frame preview.** When committing would cascade
  ("this will also delete 3 windows" — D39/D42), the tool may run one `dryRun` at commit to show that, then
  commit for real. One `dryRun`, at the boundary, not per frame.
- **Hover** highlights the snap candidate / pickable face under the cursor (recolour in the batch, the
  mechanism `#recolorPart` already provides — no re-tessellation).
- **Gizmo** (move/rotate handles on a selection) is the direct-manipulation front-end for the move/rotate
  commands (§9). It is overlay geometry + a drag that maps handle motion to `core.setPlacement`/`core.rotate`
  args, committed once on pointer-up (intermediate frames are previews). **The gizmo is proposed as design
  now but built after the move verbs are ruled — it is the most direct driver of ⓑ's arg shapes (§9).**

## §6 — Numeric entry — the thing that makes a CAD tool precise

While a tool is collecting a point, typing a digit opens a small numeric field pinned near the cursor. The
typed value **overrides the pointed dimension**: for the wall tool, typing `5000` while rubber-banding sets
the length to exactly 5000 mm along the current direction; `Tab` moves between fields (length / angle).
`Enter` commits the value as the input; `Esc` closes the field without committing. This is what makes the
gesture _exact_ rather than _approximate_, and it is why §4.4's "approximate never commits silently" holds
even when the user never snapped — they typed the truth.

## §7 — Keyboard, selection, visibility, filtering

- **Keyboard** — `Esc` (cancel), `Enter` (commit/next), digits (numeric entry), `Ctrl+Z`/`Ctrl+Y`
  (undo/redo, already commands). ⚠ There is currently **not one `keydown` handler in the app**; the
  `ToolController` owns them all in one place so focus/repeat semantics are consistent.
- **Selection / hide / isolate / filter** — missing entirely, and at 10,000 elements not optional. All
  **additive, no contract cost**: selection is an app-layer set of `nodeId`/`elementId`; hide/isolate toggles
  batch membership (the `#drawn`/`PartBatch` lifecycle already supports removal); a view filter reads what the
  model already knows — `discipline` per part (D45), `loadBearing`, `containerId`, `typeId`. **Design intent
  only in this phase** (the tool state machine + snap seam are the phase's spine); selection/filter can land
  in parallel and does not gate the freeze.

---

## §8 — The Select tool and picking (already half-built)

Select is the default tool. It uses the existing `Viewport.pick` (raycast → `SubShapeRef`) to select an
element/part, and drives hover highlighting. It is the entry point for the gizmo (§5) and for
click-a-face hosting (§4.2). Nothing new in the pick path — it is reused verbatim; Select is the state
machine wrapped around it.

## §9 — ⓑ PRE-FREEZE OBLIGATION: reserve the placement / move command shapes

**This is a freeze-gate row assigned to P4.5 and still unrecorded.** There is **no command that moves an
element** (verified: 39 CRUD commands, none touches `placement` after creation). P5 step 7 lists
`move / rotate / copy / array`; the plan's instruction is _"drive their arg shapes with a pointing device
before `Command.argsSchema` freezes — do not design `move` in the same phase that freezes it."_

**Freeze-safety (Entry 45's judgement, restated so nobody re-litigates it): this does NOT block the freeze
and I do not claim it does.** A move verb is _additive_ under D19 (a new `Command` instance is additive; only
the _shape_ of the contracts it leans on is pre-freeze), `transactionId` is already reserved on
`UndoableEdit`, and D52 folds the drag into `setParams`. **But the validation the plan asked for — driving
these arg shapes with a real pointing device — was never done, and after the freeze it is worth nothing.**
So this doc reasons the shapes out analytically from the gestures, and flags that the **empirical**
validation (build the move/gizmo tool, drive it, confirm the args are what a pointing device actually needs)
must happen during the P4.5 build, before step 6. What the analysis of the gestures teaches:

**Proposed reserved command shapes (for the owner to rule — Q4):**

| Command             | Args (proposed)                                                                     | Driven by the gesture                                                                              |
| ------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `core.setPlacement` | `{ elementId, placement: Transform[] }` — replaces the element's placement outright | The gizmo _absolute_ case and paste-in-place. Idempotent; the simplest reservation.                |
| `core.move`         | `{ elementId, by: Vec3 }` — a translation delta                                     | Drag-move. A `by` delta composes cleanly under undo and is what the gizmo produces frame-to-frame. |
| `core.rotate`       | `{ elementId, axis: Vec3, angle: number, about: Vec3 }`                             | The rotate gizmo. `about` defaults to the element's own frame origin.                              |
| `core.copy`         | `{ elementId, by: Vec3 }` → returns the new element's id in its `UndoableEdit`      | Drag-copy (Ctrl+drag).                                                                             |
| `core.array`        | `{ elementId, mode: 'linear'\|'grid', count, step: Vec3, step2?: Vec3 }`            | Array tool. Reserved shape only; body is v1.0.x.                                                   |

⚠ **The open design tension the pointing device will resolve, and why it is a question not a decision:**
`move`/`rotate` as _deltas_ vs `setPlacement` as _absolute_ is not free. A **baseline-parameterised** wall
(D52 — `{start, end}`) is moved by changing its **params**, not its **placement** — dragging a whole wall is
`core.setParams` translating both endpoints, and dragging one end is `core.setParams` on that endpoint
alone (§10). So the move verbs are for elements whose position lives in `placement` (an Opening's offset, a
GenericSolid, a placed family), while the most common "move" in the product (a wall) never calls them. **This
split — which elements are moved by `setParams` and which by `move`/`setPlacement` — is the thing a real
pointing device would confirm, and the thing I most want the owner's eyes on before it freezes (Q4).**

## §10 — ⓘ PRE-FREEZE OBLIGATION: confirm the compound edit is expressible as ONE undoable unit

**"Drag the wall's free end" is the single most common gesture in BIM, and it must be ONE undoable edit.**
Under a `{length, placement}` wall it was a _compound_ change to two fields that no command expressed — the
finding that forced the D52 baseline. **Under the D52 baseline wall (`{start, end, baseLevel, topLevel}`,
already built in `@bunyan/types`), dragging one end is a single `core.setParams` that changes `end` alone;
length is derived.** So the most ordinary gesture in the product **is** one command, one `UndoableEdit`, no
compound — **D52 already discharged the hard half of ⓘ, and this doc confirms it against the shipped Wall.**

**What still needs confirming (and is the ⓘ deliverable):**

- **Multi-element gestures that are genuinely compound** — "add a room" (four walls + a space), "drag a
  corner where three walls meet" (three `setParams` that must all apply or none). These need
  `UndoableEdit.transactionId` (reserved, currently **unused**) to bind several edits into one undo unit.
  **The design question is whether P4.5 should _exercise_ `transactionId` now** (build the corner-drag as a
  transaction and prove it undoes atomically) so the reserved field is validated before it freezes — or leave
  it reserved-and-unexercised. **Recommend exercising it** (a reserved field never driven is Entry 45's own
  warning about `move`), via the corner-drag gesture, which is the smallest real compound edit. **Owner Q5.**
- ⚠ This is freeze-relevant but **not freeze-blocking**: `transactionId` is already reserved, so exercising
  it is additive validation, not a contract change. If the exercise reveals the field's _shape_ is wrong
  (e.g. it needs to carry ordering, not just an id), **that** would be a pre-freeze correction — which is
  precisely why the plan wants it driven now.

## §11 — Exit criteria (how the phase proves itself) — for reference, not this deliverable

The build (after the rulings) is done when:

1. A wall is **drawn with a pointing device** — activate → click start → snap to a grid intersection → click
   end → rubber-band preview → type a number to override the length → commit. **Exactly one `Command`
   dispatched; the document has no intermediate state at any point.**
2. **The same edit is expressible through `window.bunyan`** with the **same resulting document state and the
   same `UndoableEdit`** — the P4 equivalence test, now against a _tool-authored_ edit. This is the machine
   proof that the tool layer smuggled in no private path, and the reason the phase sits before the freeze.
3. A window is placed by **clicking a face** — the pick resolves to a `SubShapeRef` and **no human types a
   derivation token**.
4. **An element is moved, and the wall's end is dragged**, each through a command that existed before the
   freeze.
5. **`d19-boundary.test.ts` stays green** — the tool layer holds no `KernelClient`; the snap seam is
   read-only and mints no identity.
6. **The reservations (§9) are in the contract and signed off by the Architect** before P5 step 6.

## §12 — OPEN QUESTIONS FOR THE OWNER (the design stops here for the rulings)

- **Q1 — Domain rule 17.** Adopt the rule as worded in §1 ("a tool collects input; only a command changes the
  model")? And confirm the **numbering** — a `schedule.ts` comment already says "rule 17" for a different
  (documentation) convention; should the domain rule be **17**, or the next free §8 number to avoid the
  collision?
- **Q2 — Two-tier snap seam.** Approve the recommended design: a **browser-side approximate snap index**
  (Tier 1, per-frame) with the **kernel's exact ops as the confirming fallback** (Tier 2, commit-only), and
  the "approximate never commits silently" guard-rail (§4.4)? Or require every snap to go to the kernel
  (exact, but too slow at 60 fps — not recommended)?
- **Q3 — Snap priority order.** Accept the proposed default tie-break (endpoint > intersection > midpoint >
  grid > perpendicular/extension > face > free — §4.3), or specify a different one?
- **Q4 — The move/placement command-shape reservations (ⓑ, PRE-FREEZE).** Rule the arg shapes in §9's table,
  and especially the **`setParams`-vs-`move` split**: is a baseline wall moved by `setParams` (both
  endpoints) while a placed element is moved by `core.move`/`core.setPlacement`? Delta-based (`by: Vec3`) or
  absolute (`placement: Transform[]`) — or both verbs reserved? _(This freezes at P5 step 6; it is cheap only
  until then.)_
- **Q5 — Exercise `transactionId` now (ⓘ, PRE-FREEZE)?** Build the corner-drag gesture as a real
  transaction to **validate the reserved `UndoableEdit.transactionId` shape before it freezes**
  (recommended), or leave it reserved-and-unexercised? _(A reserved field never driven is the exact risk
  Entry 45 warned of for `move`.)_
- **Q6 — Scope of the P4.5 build.** Is the phase's committed scope the **spine** — tool state machine + snap
  seam + the wall/opening/move tools + numeric entry + the two reservations — with **selection/hide/filter
  (§7) as parallel, non-gating** work? Or should selection/filtering be inside the phase's exit criteria?
