## §0 — The ruling this answers

D95 (`D-20261007-05`, Q8) answered `translate`, with this free-text, verbatim:

> a propre solution myst be found not limited to just either drop moving wals or make a general comand have wal specific knowledge in order to builde a bunyan that can rival Revit,Arhcicad and Rhino

Both framed options are therefore out: **keep refusing**, and **wall knowledge in `core.move`**. What is
wanted is a wall that moves, copies and rotates through the general verbs, with the general verbs still
knowing nothing about walls.

8 of 8 verb calls refuse, so every element of the demo scene is unmovable through the move verbs. The

any geometry is staged.

What the `setParams` road does not cover:

- **Rotate and copy have no road at all** — `setParams` cannot mint an element or turn one.
- **An agent has no move verb for a wall** (D19): the drag route exists only in the app's planner
  (`apps/web/src/tool/drag.ts` `baselineTranslatePlan`), which reads `start`/`end` by name — wall
  knowledge already sitting in the app layer.
- **Copy refuses before its hosted check runs**, which is why D94 (T-036) is unreachable on a wall.

## §2 — Every derivation that reads the baseline

The baseline is `{start, end}` in params, read through `baselineOf` (`joins.ts:106`) or by name.

| Reader                       | Where                                                                | What it derives                                    |
| ---------------------------- | -------------------------------------------------------------------- | -------------------------------------------------- |
| join spatial index           | `joins.ts` `indexOf`                                                 | which walls can meet (the O(N) grid, Entry 61)     |
| join resolver                | `joins.ts` `resolveJoins`, `resolveEnd`                              | the mitre/butt cap lines the wall builds with (0c) |
| corner topology              | `joins.ts` `endpointsOf`, `wallsShareCorner`, `wallsMeet`            | which walls share a corner                         |
| **billed axis length (D72)** | `joins.ts` `builtAxisLength`, read by `cleandelta.ts:403`            | `canonical.length`, clipped at the cap lines       |
| rebuild cascade              | `dependency.ts` `dependents`, `joinNeighboursOf`                     | which neighbours rebuild when a wall changes       |
| **room bounding**            | `room.ts` `footprintOf` (its own `readVec2` of `start`/`end`)        | the wall's two faces as room boundary segments     |
| the positioning guard        | `placement.ts` `positioningOf`                                       | the `baseline` rung that refuses today             |
| change classification        | `cleandelta.ts` `MOVE_PARAMS` (`start`, `end`, `origin`, `location`) | a params change that is a MOVE, by param NAME      |
| the wall's own build         | `packages/types/src/wall.ts` `buildGeometry`                         | the solid                                          |
| app drag / keep-live / tools | `apps/web/src/tool/drag.ts`, `tool/tools.ts`, `view/keepLive.ts`     | the drag plans, the wall tool, the visible set     |

Every one of them reads **params**. That is the constraint every candidate below is judged against: a
mechanism that moves the wall must change `start`/`end`, or it must change all ten readers.

## §3 — What "proper" has to satisfy

1. **One position, in one place.** A wall is never where its params say it is not (D80's _"in two places at
   once"_, the failure the refusal exists to prevent).
2. **No wall knowledge in the general verbs** (D95). The verbs may know about _positions_, never about walls.
3. **Reaches data families** (D61): a family authored as data must be movable the same way, without code.
4. **Honest where a motion cannot be represented.** A baseline is 2D in the Level plane, so a tilt, a
   vertical shift and a mirror of a handed element each need a named refusal, not a silent approximation.
5. **The agent gets it too** (D19): whatever moves a wall is a registered command, never an app-only path.

## §4 — How Revit, Archicad and Rhino move a wall

⚠ **Unverified here:** this box could not reach the web (WebSearch permission was not granted this
session), so the three rows below are from the author's knowledge of the published APIs and are cited by
API name only. `unverified here: §4's three rows — hmdnah to confirm` against the vendor API docs.

| Tool     | Where a wall's position lives                                                             | How the generic Move/Rotate/Copy reaches it                                                                                                                                                                           |
| -------- | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Revit    | `Element.Location` — a `LocationCurve` for a wall, a `LocationPoint` for a column         | `ElementTransformUtils.MoveElement/RotateElement/CopyElement`, implemented through `Location.Move`/`Rotate`: the element's own location type applies the transform; joined walls' ends follow by default (unverified) |
| Archicad | the wall's reference-line coordinates (`API_WallType.begC`/`endC`); no instance transform | Drag/Rotate/Mirror rewrite those defining coordinates; the generic edit does not know what a wall is                                                                                                                  |
| Rhino    | the geometry's own data (control points); a block instance carries an `InstanceXform`     | `ObjectTable.Transform(id, xform, deleteOriginal)` → `GeometryBase.Transform`, implemented per geometry class                                                                                                         |

**The common pattern:** the generic command hands a rigid transform to the element, and the element's
_definition_ applies it to its own defining data. None of the three keeps a separate placement beside a
wall's defining line. That is the shape §5's candidates A and B take; candidate C is the opposite one.

## §5 — Three candidates

### A — the schema declares which params are positions (recommended)

`ParamField` gains one optional member naming how a rigid motion acts on the field:

```ts
/** RESERVED (D95). How a rigid motion acts on this param. Absent ⇒ a motion never touches it. */
readonly motion?: 'planPoint' | 'point' | 'direction';
```

`core.wall` tags `start` and `end` as `planPoint`. The verbs then act generically:

- **An element with any tagged param is params-positioned.** `core.move`/`rotate`/`copy` apply the motion to
  every tagged param with `placement.ts`'s existing `applyMotions` (a `direction` takes the rotation only)
  and write a `core.setParams`-shaped change; `placement` is untouched. Every reader in §2 then moves with
  the wall, because the params are what moved. `positioningOf`'s `baseline` rung becomes _"params carry the
  position"_, read from the schema instead of from `baselineOf`.
- **Refused, named:** a `planPoint` param under a rotation whose axis is not vertical, or a translation with
  `dz ≠ 0` (a wall's Z is its Level, so the message names `core.updateContainer` / the `base`/`top`
  constraint); a mirror of any tagged element (§6); `core.setPlacement` on a params-positioned element (an
  absolute placement means nothing there — the message names `core.move`).
- **`core.rotate`'s default `about` changes for this class:** a wall's frame origin is the world origin
  (its placement is empty), so D80's default would orbit it across the site. The default becomes the
  centroid of the tagged points — generic, and the baseline midpoint for a wall.

Why a new member rather than `kind`: position cannot be read off `kind`. Measured — `kind: 'point'` already
types directions and offsets (`commands.ts` `normal`, `direction`, `axis`, `by`), and a wall's `start`/`end`
are `kind: 'array'`, not `'point'`.

**Cost.** One optional member and its string union in `schema.ts`, a watched file ⇒ `RISK:
contract-touching`, owner merge (`docs/INVARIANTS.md §2.1`). **Must land before P5 step 6:** after it,
widening `ParamField` is an amendment across three products and the generated agent tool list (the same
reason `refTo` was widened pre-freeze, D81). The verb bodies and the `wall.ts` tags are not frozen and may
follow the freeze. **Reaches data families for free:** `FamilyDefinition.parameterSchema` is a
`ParamSchema` (`families.ts:180`). It also makes `cleandelta.ts`'s by-name `MOVE_PARAMS` and `drag.ts`'s
`start`/`end` reads derivable from the schema (follow-ups, not part of the mechanism).

### B — the Type implements the motion (Revit's `Location.Move`)

`BimObjectType` gains `applyMotion?(params, motion): Params | { refused: string }`; the verbs call it when
present and fall back to `placement` when absent. The verbs stay wall-free; the Type owns its own geometry,
and only this candidate can mirror a handed wall correctly (it can swap `start`/`end`, §6).

**Cost.** One optional member on `BimObjectType` in `types.ts`, a watched file ⇒ contract-touching, owner
merge, **before P5 step 6** for the same reason as A. **Fails requirement 3:** a data family carries no code,
so D61 families stay unmovable by params until a second, data-side reservation exists. The motion is also
opaque to the generated agent tool list — an agent cannot learn which params a move will change.

### C — fold the placement into the baseline

Let `core.move` write `placement` on a wall as it does on a GenericSolid, and make `baselineOf` return the
placed baseline. No frozen member; it could land after the freeze.

**Rejected:** it fails requirement 1 by construction. The params keep saying `[0, 0] → [4000, 0]` while the
wall stands 5 m away, so every reader in §2 that does not route through `baselineOf` (`room.ts`
`footprintOf`, `cleandelta.ts` `MOVE_PARAMS`, `drag.ts`'s corner matching, the property panel, the agent's
`query`) reads the wrong place silently — D80's measured _two places at once_, made permanent instead of
refused. A non-vertical rotation would also leave a baseline that is no longer in its Level plane.

### Comparison

|                                   | A — schema tag                     | B — Type hook                             | C — fold placement |
| --------------------------------- | ---------------------------------- | ----------------------------------------- | ------------------ |
| Wall knowledge in the verbs       | none                               | none                                      | none               |
| One position, one place (req. 1)  | yes                                | yes                                       | **no**             |
| Data families (req. 3)            | yes, free                          | no — needs a second reservation           | yes                |
| Agent can see what moves (req. 5) | yes, in the schema                 | no                                        | yes                |
| Mirror of a handed wall           | refused (§6)                       | correct                                   | wrong silently     |
| Frozen-surface cost               | `ParamField.motion?` (`schema.ts`) | `BimObjectType.applyMotion?` (`types.ts`) | none               |
| Must land before P5 step 6        | **yes** (the member)               | **yes** (the member)                      | no                 |

**Recommendation: A.** It is the only candidate that meets all five requirements of §3 in v1.0.0; B's one
advantage (mirror) has no v1.0.0 verb that needs it, and B can still be reserved beside A if the owner
wants it (`D-20261012-03`, option `both`).

## §6 — Mirror

No v1.0.0 verb mirrors, but `core.setPlacement` accepts a `mirror` motion. Mirroring a wall's two points is
not a mirror of the wall: across the x-axis, `[0, 0] → [4000, 0]` maps to itself, while the true mirror
image has its layer stack on the other face. A wall is _handed_ (its a-side is the left of `start → end`,
`wall.ts`), so a correct mirror also swaps `start` and `end` — Type knowledge. Under A it is refused with
that reason; under B the Type does it.

## §7 — Joins after a move, and what depends on this answer

**The moved wall's joins.** Moving a wall's params moves it off its corner; its partner keeps its end and
the auto-mitre dissolves, exactly as a `core.setParams` translate does today. Revit (unverified) drags the
joined ends along. Making `core.move` do that requires `wallsJoinedTo` in the verb — wall knowledge — so the
default keeps the verb single-element and leaves _follow_ to the gesture: the app composes the neighbours'
`core.setParams` under one `transactionId`, as `cornerDragPlan` already does. `D-20261012-04`.

**D94's deep-copy (T-036).** Today every wall copy refuses at the `baseline` rung before the hosted check.
Under A or B the copy translates params, reaches the hosted check, and T-036's deep-copy runs there: an
opening is positioned by `offsetU`/`offsetV` relative to its host face, so a re-pointed `hostRef` lands it
on the copy with no offset arithmetic. T-036 stays `blocked` until the chosen mechanism is built (a new
row the steward sequences, after `D-20261012-03`); its _"a join override still refuses"_ item matches
`D-20261012-04`'s default. Under C the copy would reach the hosted check too, with the copy's params lying.

**`D-20261007-08` (Q20, the ribbon).** Its case for withholding `core.move` is the measurement in §1 —
`core.move` refuses on every demo element. Once A or B is built that stops being true, leaving
`core.array` as the only withheld verb, which is the single-entry case Q20's `app-list` default is built
for. Q20's answer does not change this design.

## §A — The probe (§1's command)

Saved as `tests/t035-probe.test.ts`, run, then deleted.

```ts
import { afterAll, beforeAll, expect, it } from 'vitest';
import { KernelHost } from '@bunyan/kernel-core';
import { InProcessTransport, KernelClient } from '@bunyan/kernel-client';
import { createOcctKernel } from '@bunyan/kernel-occt';
import {
  CORE_COMMANDS,
  CommandFailure,
  DocumentContext,
  baselineOf,
  createRegistries,
} from '@bunyan/document';
import { openingType, wallType } from '@bunyan/types';
import { seedDemoScene } from '../apps/web/src/scaffold/seed.js';

let client: KernelClient;
beforeAll(async () => {
  client = new KernelClient(new InProcessTransport(new KernelHost(await createOcctKernel())));
});
afterAll(() => client.dispose());

it('T-035 probe', async () => {
  const r = createRegistries();
  r.types.register(wallType);
  r.types.register(openingType);
  for (const c of CORE_COMMANDS) r.commands.register(c);
  const doc = new DocumentContext({ registries: r, geometry: client });
  await seedDemoScene(doc);
  const rows: string[] = [];
  for (const el of Object.values(doc.scene.elements).filter((e) => baselineOf(e) !== undefined)) {
    const b = baselineOf(el)!;
    const tries: [string, Record<string, unknown>][] = [
      ['core.move', { elementId: el.id, by: [1000, 0, 0] }],
      ['core.copy', { elementId: el.id, by: [1000, 0, 0] }],
      ['core.rotate', { elementId: el.id, axis: [0, 0, 1], angle: 90 }],
      [
        'core.setPlacement',
        { elementId: el.id, placement: [{ kind: 'translate', by: [1000, 0, 0] }] },
      ],
      [
        'core.setParams',
        {
          elementId: el.id,
          params: {
            start: [b.start[0] + 1000, b.start[1]],
            end: [b.end[0] + 1000, b.end[1]],
          },
        },
      ],
    ];
    for (const [cmd, args] of tries) {
      try {
        await doc.execute(cmd, args, { dryRun: true });
        rows.push(`${el.id} ${cmd} ACCEPTED`);
      } catch (e) {
        const f = e as CommandFailure;
        rows.push(
          `${el.id} ${cmd} ${f.code} ${/BASELINE params/.test(f.message) ? 'baseline-rung' : f.message}`,
        );
      }
    }
  }
  console.log(rows.join('\n'));
  expect(rows.length).toBeGreaterThan(0);
}, 60000);
```
