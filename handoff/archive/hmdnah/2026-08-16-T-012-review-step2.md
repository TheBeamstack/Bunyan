## 2. Item 3 — new kind of thing

`seatFromBranchPrefix`/`reviewerForBranch` are a new routing axis (by branch prefix, not by title). What
quantifies over "every seat": `seatFromBranchPrefix` calls `readRegistry(root).some((r) => r.seat ===
prefix)` — a fresh read of `docs/seats/README.md`'s table between the `BEGIN/END SEATS` markers on every
call, not a hardcoded array. `reviewerForBranch` then calls `machineOf(root, fromSeat)` (also
`seatRow(root, seat)` → `readRegistry(root).find(...)`) and hands the result to `reviewerFor`, which
itself re-reads the registry (`readRegistry(root)` at its own top). Grepped `scripts/seats.mjs` and
`scripts/agent-start.mjs` for hardcoded seat names outside comments/docstrings/CLI-usage examples: none —
every seat name that appears in executable logic in this diff comes from the registry, never a literal.

Confirmed: a sixth seat added as a new row in `docs/seats/README.md` gets correct branch-prefix routing
automatically the next time these functions run — no matching code update needed anywhere in this path.
This is the registry doing the quantification, not a list that could silently drift from it.

## 4. Independent spot-check

Read `reviewerForBranch`'s actual implementation directly (`scripts/seats.mjs:443-451`) rather than
trusting step 1's report:

```js
export function reviewerForBranch(root, branchName, finishingSeat) {
  const fromSeat = seatFromBranchPrefix(root, branchName);
  if (!fromSeat) {
    return { seat: null, solo: false, reason: `branch '${branchName}' names no registered seat...` };
  }
  const m = machineOf(root, fromSeat);
  return { ...reviewerFor(root, m, finishingSeat), reason: null };
}
```

Confirmed for myself: it resolves the branch's seat, resolves that seat's machine via `machineOf`
(a plain registry lookup), then spreads the return of `reviewerFor(root, m, finishingSeat)` — the exact
same function a `T-nnn` PR's title-based routing calls. It does not reimplement any machine-resolution or
reviewer-selection logic of its own; the only new logic here is deriving `m` from a branch prefix instead
of a task id. Matches step 1's claim.
