## 3. DEFECT 1 (blocking) — the option edge never reaches the JOIN neighbour, so it reproduces D68 from the authoring side

`dependency.ts`'s new case seeds `belongsToDescendants(scene, elementsTaggedIntoSet(scene, setName))` —
every element whose own tag names an option in the changed set, plus everything hosted or parented on one.
It does **not** expand over `wallsJoinedTo`, which the `elements` case does (line 82) for exactly this
reason.

That omission is the defect, because the elements whose *own* active-ness flips are not the elements whose
*geometry* changes. A wall going inactive is precisely what changes a **different** wall's miter —
`partnersAt` filters by `isElementActive` (`joins.ts:322/358/416`), which is the mechanism the case's own
comment cites as the reason this edge is not a declared "nothing".

**Measured end-to-end, through the shipped verbs, real OCCT kernel.** Main-model wall `M` = `[0,0]→[6000,0]`,
option-A wall `W` = `[6000,0]→[6000,4000]` tagged into option A (primary). Then
`core.updateDesignOption { id: B, isPrimary: true }`:

```
resolveJoins(M) BEFORE the promote → ['end']     (M miters against W)
resolveJoins(M) AFTER  the promote → []          (A is demoted, W is not active, the miter is gone)

#affected for that edit — edit.rebuilt ∪ dependents(change) for every change —
  named: [ wall-…GBPRCWQH0R ]                    ← W, the option wall, only
  main:  wall-…966QP1J                           ← M, NEVER NAMED
```

Both `resolveJoins` assertions are ground truth and both passed; the failure is the third. `M` is not
re-staged, so `M` keeps a solid mitered against a wall the document no longer builds — `join-option-cascade.test.ts`'s
own mode 1, arriving through the invalidator instead of through the resolver.

T-011's own `done-when` names this exactly: *"an option edit changes which walls the join resolver can see
(D68's ambiguity flip), so a 'nothing' here reproduces D68 from the authoring side."* The edge is not a
"nothing" — but it under-names, and the outcome is the same defect one step removed.

**Fix shape** (`zayd`'s call, not mine): run the seed set through `wallsJoinedTo` the way `case 'elements'`
does, or fold the option edge into it. The case's own comment already states the standard it misses —
*"over-naming costs a rebuild; under-naming leaves a stale solid."*

## 4. DEFECT 2 (blocking, same site) — undoing a delete re-stages nothing

`DocumentContext` computes `#affected` against `this.#scene`, the **pre-change** scene, on all three paths
(`execute` line 367-368, `undo` line 451, `redo` line 493). Forward that is correct. On **undo of a
delete** it is not: the pre-revert scene is the post-delete one, the option is already gone from the
catalogue, and `elementsTaggedIntoSet` resolves the seed through `setName → optionIds → elements` rather
than through the option's own id — so the deleted option's own tagged elements fall out of the filter.

```
dependents(sceneWithOption,    {designOptions, id:'option-a', before:OPT_A}) → [ 'w-opt-a' ]   correct
dependents(sceneWithoutOption, {designOptions, id:'option-a', before:OPT_A}) → [ ]             ← undo
```

Reachable through the shipped verbs: `core.deleteDesignOption { id, acknowledge: true }` on a set's only
option is accepted (`checkPrimaryInvariant` returns early when the merged set is empty, and `acknowledge`
suppresses the referrer guard), the tags dangle ⇒ `ownTagActive` returns `false` ⇒ the elements go
inactive; `undo()` restores the option, they go active again, and nothing is re-staged.

`dependents`'s own `@param scene` docstring (`dependency.ts:47-49`) still asserts *"the pre- or post-edit
scene gives the same answer"* — true for the container/grid edges it was written for, **false for this
one**. That is an item-4 claims-vs-code miss inside the diff as well as the defect itself.

**Fix shape:** seed by the changed option's **own id** (`e.designOptionId === option.id`) union the set's
siblings, rather than by set membership resolved out of a catalogue that may no longer contain it.

## 8. Ruling on the scope question `zayd` raised for a reviewer

> Two of the swept comment sites (`isElementActive`'s *"nothing calls it"*, `ViewCommon`'s *"no body reads
> yet"*) were already false **before** this PR rather than falsified by it, and were swept anyway.

**Ruled in scope, and correctly handled.** Both claims verified false on `main`: `git grep -c
isElementActive main` matches in `enumerate.ts` (2), `cleandelta.ts` (2), `joins.ts` (4) and `room.ts` (2),
and `designOptionIds` is read on `main` in both `view.ts` and `commands.ts`. The reasons, in order of
force:

1. `AGENTS.md §3` row 1 is unconditional — *"a design doc contradicts itself or the code ⇒ fix the doc.
   Never code around it silently."* It carries no "only if your diff caused it" qualifier.
2. Invariant 7 **is** the instruction to go past the diff: *"enumerate every existing site the rule
   governs, and check each one."* A sweep bounded by what the diff falsified is the narrower sweep
   invariant 7 was written against, and it is how a site stays wrong through nine consecutive turns.
3. `AGENTS.md §7.3` — *"record what is true now."* When a sentence became false does not change whether it
   is false.
4. The cost is nil and measured: comment-only edits in files already in the diff,
   `tests/protocol/reserved-classes.test.ts:85` has the case for it, and §7 above confirms the frozen
   surface still moves exactly one declaration.

**The boundary that makes the ruling operable, since it will recur:** a comment/doc correction found by an
invariant-7 sweep lands in the PR that found it; a **code** change found by the same sweep goes to
`docs/BACKLOG.md ## Discovered` unless it is the defect the task exists to fix. `zayd` applied exactly that
split — the two comment sites in, the `pnpm state` staleness and the `_baselinedAtEntry` cry-wolf out.
