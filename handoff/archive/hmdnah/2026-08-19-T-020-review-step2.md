## 2. Backward sweep — the populations a duration ranking cannot contain

The rule this PR puts in force is *anything outliving vitest's default deadline needs an explicit
timeout*, and the author swept it over **tests, ranked by measured duration**. Two pre-existing
populations that ranking does not reach.

**Hooks carry their own default, and it is a different number.** `hookTimeout` resolves to **10 000 ms**
independently of `testTimeout` (`node_modules/vitest/dist/chunks/coverage.DM_a_rWm.js:539`,
`resolved.hookTimeout ??= resolved.browser.enabled ? 3e4 : 1e4`), and every kernel suite's `beforeAll`
boots OCCT. The `queueMicrotask` mechanism applies to a hook exactly as to a test, so vitest 2 was not
enforcing this deadline either — the bump switches on two gates, and the author's sweep covers one.

Measured rather than read: the full suite is **green at `--hookTimeout=1200`** (97 files, 936 passed), so
every hook without an explicit timeout finishes inside 1.2 s — **≥8× margin** to the deadline now being
enforced.

⚠ Minor correction to step 1's framing: `tests/geometry-cache-d29.test.ts:59`'s `}, 120_000)` is the
**hook's** timeout, not that file's test's. The 1921 ms test step 1 named as next-slowest is genuinely
unprotected, which is the right reading — just not for the reason the call site suggests.

**Nothing is gated out of the ranking.** A test that does not run on this box would never appear in a
duration table measured on it. There are **zero** `.skip` / `.skipIf` / `.only` / `.todo` / `.runIf`
sites in the repo — one `describe.each` (`tests/geometry-queries.test.ts:29`) and nothing else — so the
box's ranking is the whole population, not a subset of it.

## 6. Weak green

### The same 936 tests could run and assert less

Step 1 strengthened the count to an empty symmetric difference on `(file, test title)`, which proves the
same tests **ran**. It does not prove they **asserted**: a suite whose setup silently no-ops under the new
runner leaves a loop with nothing to iterate, and a test executing zero `expect()` calls is green under a
title that is still true.

Instrumented. A temporary setup file (untracked, since deleted; CI never saw it) recorded
`expect.getState().assertionCalls` in an `afterEach` keyed by `(file, title)`, and the full suite ran
under each runner installed from its own lockfile via `pnpm install --frozen-lockfile`:

| | `vitest@2.1.9` | `vitest@4.1.10` |
| --- | --- | --- |
| tests | 936 passed · 97 files | 936 passed · 97 files |
| distinct `(file, title)` keys | 912 | 912 |
| keys present under one runner only | — | **0** |
| **total `expect()` calls executed** | **5047** | **5047** |
| tests whose count differs | — | **0** |

Not one test asserts less under the new runner. That is the check `(file, title)` equality cannot make.

⚠ What it still does not catch: it counts `expect()` invocations, not what they assert. A matcher that
became weaker while being called the same number of times would pass this instrument.

### The hole both runners could share

936 · 97 · 287 agreeing under both runners proves nothing if **both** miss a file.
`find tests apps -name '*.test.ts' -o -name '*.test.tsx'` returns **97**, and the 4.1.10 summary's
`testResults` is the **identical set** — zero on disk but uncollected, zero collected but not on disk.

### Is anything else under the enforced deadline by luck?

The full suite is **green at `--testTimeout=2500`**; an explicit per-test timeout still wins, so the flag
bites exactly the unprotected population. Every test without an explicit timeout is therefore under
2500 ms — **≥2× margin**. Measured maximum 1921 ms (`geometry-cache-d29`). Exactly three tests exceed
5000 ms — 57 806 / 18 585 / 16 306 ms — and all three carry explicit timeouts, one of them added here.

### Where the bump changes semantics rather than enforcement

One site: `tests/kernel-client.test.ts:137-155`, the repo's only `vi.useFakeTimers`, and vitest 3 began
faking `performance.now` too. Read against the code, it advances 5001 ms and awaits
`expect(pending).rejects.toSatisfy(… code === 'TIMEOUT')` — if the faked timer never fired the await hangs
rather than passing vacuously, and the test carries no explicit timeout, so it passed at
`--testTimeout=2500` under real enforcement. Not weak.
