## 4. The one failure, and why it is not a regression

The first full run under 4.1.10 was `935 passed | 1 failed`:
`tests/document-persistence.test.ts > ⚠⚠ THE CLEAN DELTA IS COMPUTABLE FROM A .bnn`, *Test timed out in
5000ms*.

Reproduced in isolation, so it is not worker contention. A/B on the same commit and the same file, each
runner installed in turn:

| runner | duration of that test | result |
| --- | --- | --- |
| `vitest@2.1.9` | **18 549 ms** | ✓ passed |
| `vitest@4.1.10` | **18 397 ms** | ✗ timed out at 5 000 ms |

The test's own cost did not move — 0.8%. What moved is enforcement: **vitest 2 never applied the 5 000 ms
default timeout to this test.** `InProcessTransport` delivers every kernel response through
`queueMicrotask` (`packages/kernel-client/src/transport.ts:63`), so 250 real kernel edits are one
uninterrupted microtask chain; the event loop never reaches the timer phase, and a `setTimeout`-based
deadline never fires. The test was 3.7× over a limit nobody was checking.

That is `AGENTS.md` invariant 8 in its purest form — a green test proved only what the runner bothered to
assert — so the fix is the explicit timeout the rest of the suite already uses for real-kernel tests, not
a config-wide `testTimeout` that would re-hide it:

```ts
  }, 120_000);
```

**Backward sweep over the newly-enforced rule.** Every test in the suite, ranked by measured duration:
exactly three exceed 5 000 ms, and the next-slowest is 1 980 ms — a 2.5× margin.

| test | ms | explicit timeout |
| --- | --- | --- |
| `document-build-cost-scale.test.ts` — prices one more element | 58 571 | `600_000`, pre-existing |
| `document-persistence.test.ts` — the clean delta | 18 489 | `120_000`, **added this turn** |
| `document-scale.test.ts` — a five-storey building rebuilds | 16 256 | `180_000`, pre-existing |
| `geometry-cache-d29.test.ts` — the attribution | 1 980 | none needed |

The two pre-existing ones were already covered, which is why the bump surfaced exactly one test. The
sweep is over durations rather than over source, because the rule quantifies over *how long a test takes*
and only a run can answer that.

⚠ **The margin is a measurement on this box, not a guarantee.** A slower machine could take a 2 s test
past 5 s, and the pc is the machine that has not run this suite at all yet — T-021 is where that gets
measured.
