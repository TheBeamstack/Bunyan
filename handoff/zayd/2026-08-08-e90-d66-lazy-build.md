## 2 · D66 — lazy build, measured first

`docs/design/P5_step9_D66_lazy_build_design.md` is the deliverable;
`tests/d66-lazy-build-measure.test.ts` is the instrument and ships with it. TASK's three questions:

### 2a · What fraction of a cold load is FORCED? **~35%.**

54 elements, 3 storeys, loaded from `scene.json` with no cache:

```
(A) rebuildAll     1271 ms   23.5 ms/el
(B) first storey    452 ms   25.1 ms/el   ← 35.5% of (A), for 33.3% of the elements
(C) the rest        831 ms                 (deferred)
(B)+(C) vs (A)     100.9%                  ← two-pass overhead ~1–4.5%
```

**64.5% of the cold load is deferrable**, cost fraction ≈ element fraction ⇒ **no fixed floor worth
buying back at this size.**

⚠ **AND THE HONEST HALF, WHICH THE ROW MUST KEEP:** one storey of a **10k** tower is still ~1,000
elements ≈ **24 s**. **Lazy build moves the cold load from unusable to bad. It does not close §1a's row**,
and I have not re-coloured it. Closing it needs `instantiate` (RESERVED) or MT (v1.0.x).

### 2b · What does it cost the INVARIANT? **Nothing measurable — and the join is why that is not obvious.**

A partially built document agrees with a fully built one, element for element (part node ids + the full
`quantities` breakdown), including a wall carrying a **window** (the CUT node mints sub-shape names), and
a second pass is not a different building.

⚠⚠ **The one that could have sunk it: a wall's geometry is not a function of the wall alone.**
`resolveJoins` clips its ends against its neighbours, so _"build A, never build B"_ invites **D68's exact
silent-wrong shape — a wall that should be mitred coming out with a plain cap, which nothing would
flag.** Measured on the **real shipped D52 wall** (`{start,end}`, auto-mitring): a wall whose corner
partner is **never built** is **identical** to the same wall in a full document.

**Because `resolveJoins` reads `scene.elements` — the RECIPE — never the built set.** Nothing in the
geometry pipeline is a function of what is in the heap. ⚠ The existing scale fixture is blind to this
(its walls are `{length,height}`, so `baselineOf` returns `undefined`), which is why the test builds its own.

### 2c · Is it contract-shaping? **No — the build half needs no new API at all.**

**`rebuildOnly(ids)` IS the lazy-build primitive and has shipped since 2026-07-25**, written for the Clean
Delta so a 38-element delta would not cost a whole-model rebuild. _"Build what is named, not what
exists"_ is the same sentence a first paint needs. `releaseShape` (frozen) and `dispose()` cover eviction.
**D66's build half is a caller, not a feature.**

### 2d · ⚠⚠ I predicted the Q19 shape and the measurement said no

The interesting question was what a lazily-loaded document tells a **take-off**. I expected the shape this
project has met four times — a short number wearing `basis: 'exact'`, every diagnostic empty. Measured, 4
walls authored, 1 built:

```
FULL : 8 rows · 12,040,000,000 mm³ · basis exact · unmeasured 0
LAZY : 2 rows ·  3,010,000,000 mm³ · basis exact · unmeasured 3   ← all three NAMED
brokenRefs 0 · unbuildable 0
```

**75% short and nothing vanished.** `projectQuantities` tests `element.state !== 'valid'` **before**
`hasParts`, so an unbuilt element takes the `unmeasured` branch by name; the silent `continue` is reached
only by a pure void or pure composite. **Entry 58's ruling already covers the element lazy build creates.**

⇒ **That honest channel, not the timing, is what makes D66 shippable** — and read the other way it is the
design constraint: **the hook D66 needs is not in the renderer, it is in the ENUMERATION.** An aggregate
must build what it is about to measure. Recorded in the design doc §3c, with the one genuinely open sub-question
(**`save` must FORCE, not DECLARE** — a save that omits unbuilt elements is data loss, not a reporting
choice) flagged as **a claim I did not measure.**
