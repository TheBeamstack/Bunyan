# T-046 — A hostile `.bnn` is refused before it inflates past an entry-count or size cap

- seat: zayd (builder, box) · account: davidian-abdo
- branch: `task/T-046-a-hostile-bnn-is-refused-before-it-infla`
- task: `docs/BACKLOG.md` T-046 · risk: high · implements: spec §9 (import hardening) · design §3, §5 · D29

## Changed

- `packages/document/src/bnn.ts`: four exported caps (`BNN_MAX_ENTRIES` 40,000, `BNN_MAX_ENTRY_BYTES`
  256 MiB, `BNN_MAX_TOTAL_BYTES` 512 MiB, `BNN_MAX_RATIO` 200:1, the ratio checked only above 1 MiB).
  `checkEntry` refuses with a message naming the cap. `loadBnn` runs `checkCaps` first, a central-directory
  pass whose filter returns `false` for every entry, so it inflates nothing. `geometryCacheReader.read`
  checks inside its single filter, because the reader keeps the caller's bytes rather than a copy.
- `tests/bnn-zip-caps-t046.test.ts` (new, 7 tests).

## Verified

- Why declared sizes are enough: fflate 0.8.3 `unzipSync` inflates into `new u8(originalSize)` with resize off
  (`esm/index.mjs:2704`, `:241`), and a stored entry copies `size` bytes of the file itself.
- Calibration at the 16k target (`node` script: 16,000 walls + 16,000 `.brep` of 3,817 B through fflate
  `zipSync` level 6): 16,001 entries, 67,204,691 B inflated, the largest entry `scene.json` at 6,132,691 B,
  ratios: `scene.json` 33.5:1, `.brep` 3.5:1, 50 MB of zeros 1024.6:1.
- Test-first: `pnpm exec vitest run tests/bnn-zip-caps-t046.test.ts` before `bnn.ts` → 5 failed, 2 passed
  (the corrupt-lead baseline and the 16k open hold today); after → 7 passed.
- Revert-verify: the `index >= BNN_MAX_ENTRIES` check removed, same command → 1 failed (the entry-cap test),
  6 passed; restored → 7 passed.
- `pnpm verify` green: `pnpm test` 103 files / 950 tests; `docs:check` 66 passed.

## done-when

- Bounds before `unzipSync` inflates anything, in `loadBnn` and `read`; each cap named, its comment states
  the figure: yes.
- Entry cap, size cap and high-ratio entry each make `loadBnn` throw naming the cap, and inflate nothing
  past it; the 16k target opens: yes. Every hostile zip starts with a corrupt DEFLATE entry, so if
  anything were inflated first the error would read "not a readable .bnn package" instead.
- Revert-verified on the entry-count bound: yes.
- No `[frozen_surface]` watched file changes (`bnn.ts` is not watched): yes.

## notes

- A total-cap test is also included (three entries, each under the entry and ratio caps).
- The cap figures are headroom over one synthetic 16k file, which has no real BRep and no long journal.
  R4's measurement of the compressed cache (design §5) is what should move them.
- A refused cap error is not wrapped in "not a readable .bnn package"; it reaches the caller as thrown.

## Changed (fix)

- `packages/document/src/bnn.ts`: new `entryRoom` walks the central directory and gives each entry the bytes
  from its local data start to the next local header or the central directory. `checkEntry` measures the
  ratio against `min(declared compressed size, room)`, in `loadBnn`'s pre-pass and in `cache.read`. Two
  entries on one local header are refused (they would count one span twice), as is zip64 (fflate 0.8.3
  only reads it, so `saveBnn` never writes it).
- `tests/bnn-zip-caps-t046.test.ts`: +2 tests (the reviewer's probe; a shared local header). The total-cap
  test now uses 1.2 MiB of incompressible bytes per entry, because it had declared a compressed size its
