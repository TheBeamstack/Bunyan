## 4. Item 6 — WEAK GREEN

For each of the five assertions in `tests/kernel-glue-growable-decode.test.ts`: what would it take to
pass while its own title is false?

1. **`has exactly the two decode sites the post-link patch knows about`** — the tripwire, and it is what
   stops the two below being vacuous. It counts rather than reads, so it cannot distinguish "the two
   `postlink.mjs` knows" from "two others"; that residue is closed on the recipe side, where
   `postlink.mjs` requires each pattern to match exactly once and exits 1 otherwise. **Re-confirmed by
   execution:** applying it a second time printed `expected exactly 1 UTF8ArrayToString decode site to
   patch, found 0` and exited **1**. The SKIP is closed.
2. **`hands neither of them a subarray of the heap`** — this is the one that could be weak, so it was
   attacked rather than read. `decodeSites` takes a fixed **120-character window** from `.decode(`,
   which runs well past the call and into the fallback loop, so both assertions read text that is not
   the decode argument. Two falsifications were constructed and measured against the real artifact:

   | variant | count | no-`subarray` | both-copy | suite |
   | --- | --- | --- | --- | --- |
   | committed (patched) | ✔ | ✔ | ✔ | GREEN |
   | A — reverted to `subarray` (the real defect) | ✔ | ✘ | ✘ | **RED** |
   | B — genuinely shared view written **without the token `subarray`**: `decode(new Uint8Array(heapOrArray.buffer,idx,endPtr-idx))` | ✔ | ✔ | ✘ | **RED** |

   Variant B is the interesting one: it evades the `subarray` scan entirely and is still caught,
   because assertion 3 demands an **affirmative** `.slice(` in each window and the emitted trailing text
   contains none. The pair is therefore stronger than either half.
3. **`hands both of them a copy instead`** — see above. **Residual weakness, recorded not fixed:** the
   window is bounded by a character count rather than by the call, so a defective argument that
   happened to be followed by an unrelated `.slice(` within 120 characters would pass. No variant I
   could construct from real emitted text does this, and assertion 1 bounds the blast radius, so it is
   an opinion under `REVIEW.md`'s table and not a blocker.
4. **`measures WHY slice is the fix`** — the load-bearing one, and it is not a text assertion: it builds
   a resizable `ArrayBuffer` and measures `subarray().buffer.resizable === true` against
   `slice().buffer.resizable === false`. It cannot pass vacuously; a non-resizable buffer fails the
   first expectation. ⚠ It measures `Uint8Array` only, while site 2 slices a `Uint16Array` — the spec
   path is the same and this is a note, not a defect.
5. **`is applied by the recipe, so a relink cannot drop it`** — a `toContain` on `link.sh`, the weakest
   of the five, and §1's relink is what actually discharges it: the recipe ran and produced the
   committed bytes.

**And the semantic check the three text assertions do not make.** `slice` was read against both call
sites rather than trusted. `UTF8ArrayToString` is reached with a **plain `Array`** from four TTY
callers (`tty.output.push(val)`), where `.slice` would return an `Array` and `TextDecoder.decode` would
throw — but emscripten's own guard is `if(endPtr-idx>16 && heapOrArray.buffer && UTF8Decoder)`, and a
plain `Array` has no `.buffer`, so the copy path is unreachable from there. Index semantics are
identical (`slice` and `subarray` both take element indices and both clamp), so the patch changes
allocation and nothing else, at both sites.
