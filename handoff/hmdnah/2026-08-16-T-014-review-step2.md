## 2. The live-exercise finding — the real defect

Ran the actual mechanism (`node scripts/agent-start.mjs --seat hmdnah --review`) rather than only reading
code. It reported **STEP 1**, not step 2 — despite step 1's report already being on record. PR #28 carried
no `review/step-1` label; `gh api repos/.../issues/28/timeline` shows no `labeled` event ever fired.

Root cause, reproduced directly against the real GitHub API (`gh label create`/`gh label edit`), not
guessed: `scripts/seats.mjs`'s `STEP1_LABEL_DESCRIPTION` was **104 characters**. GitHub caps a label
description at **100**. `gh label create --description "..."` refuses anything longer. That call is the
*only* code path that ever creates `review/step-1` (`agent-finish.mjs`'s step-1 finish, "the label is
created if absent" — necessary because the label does not exist on a fresh repo). So the very first
`risk: high` review this mechanism ever ran — this one — could never create its own routing label. That is
why the label was never applied, regardless of what step 1's session actually ran.

**Revert-verified against the real API**, not only the unit test: `gh label edit review/step-1
--description "<the original 104-char string>"` returns `HTTP 422 … description is too long (maximum is
100 characters)`. Restoring the shortened (79-char) string succeeds. Also added a permanent regression
test — `tests/protocol/seats.test.ts`, `STEP1_LABEL_DESCRIPTION.length <= 100` — since the fixture suite
cannot exercise the real `gh` call this defect lives in; watched it fail RED (`expected 104 to be less
than or equal to 100`) against the original string, GREEN against the fix. Commit `a9efe15`.

**Unblocked this review by hand**, matching exactly what the fixed `agent-finish.mjs --step 1` now does:
`gh label create review/step-1 --color 0E8A16 --description "<fixed 79-char string>"` (label already
existed from an earlier probe of mine with an empty description — corrected via `gh label edit` to the
exact fixed constant) then `gh pr edit 28 --add-label review/step-1`. This is not re-implementing step 1's
judgment — step 1's actual review content is on record and already reconciled above — only the mechanical
label-application step was ever blocked by this bug.

Posted as https://github.com/Davidian-Abdo/Bunyan/pull/28#issuecomment-5305750633.
