1. **`brokenRefs()` emits two entries identical in `elementId` and `ref`.** `danglingAncestorRefs` checks
   the two edges independently, so an element naming the same missing id on both yields two
   `BrokenReference`s differing only in `reason`. Measured on a hand-assembled scene:

   ```
   [ { elementId: 'orphan', ref: 'ghost', hostId: 'ghost', reason: 'its hostId names "ghost"…' },
     { elementId: 'orphan', ref: 'ghost', hostId: 'ghost', reason: 'its parentElementId names "ghost"…' } ]
   ```

   `App.tsx:1096` keys that list on `` `${b.elementId}:${b.ref}` ``, so the two rows collide on one React
   key. Re-measured through the shipped verbs rather than a hand-assembled scene — a door created in a
   wall, `core.setElementMetadata { elementId: door, parentElementId: <that wall> }` (no cycle, so the
   Entry 87 guard allows it), then the wall dropped the way a foreign writer would (D43): **2 entries, 1
   distinct key.** `agent.ts:218` projects `{ elementId, ref, reason }`, so the agent surface reports the
   same element twice too.

2. **The edit label was not swept with the cascade.** `core.deleteElement` still builds
   `Delete ${type.label} and ${doomed.length - 1} hosted element(s)`, which now counts members hosted on
   nothing. The label is journalled (D40), so the wrong word lands in the record and not only in the UI.
   Measured on two walls joined by `parentElementId` alone: `"Delete Wall and 1 hosted element(s)"`, two
   ids in `edit.changes`.

3. **Recorded, not proved harmful: `BrokenReference.hostId` diverges from the class T-007 landed a day
   earlier.** T-007 sets `hostId: element.id` with a stated reason; this sets `hostId: ancestorId`, an id
   that by construction is not in `scene.elements` and on the parent edge is not a host at all. No
   consumer reads the field and no test asserts it, which is why it is a note: the first consumer to
   resolve `broken.hostId` against `scene.elements` gets `undefined`.
