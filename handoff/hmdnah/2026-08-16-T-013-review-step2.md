## 2. Item 3 — new kind of thing

The guard is a single call, `identityGate(seat, account, resolveGhLogin(root))` at
`agent-start.mjs:347-349`, sitting immediately after seat/role/machine/account resolution and strictly
before every later branch in the same linear `main()` — `--review`, `--continue`, `--no-claim`,
`wantTask`, and the `role === 'steward'` path (line 718) are all resolved after it. `BUNYAN_SEAT` and
`--seat` both feed the same `parseArgs` into the same `main()`; there is no second CLI entry point
(`identityGate`/`findTaskPR`/`resolveReviewStep` are exported for unit testing, but `main()` only runs
when the file is the process entry point, per the bottom `if (process.argv[1]?...)` guard). Read the code
directly rather than trusting the diff: every seat and every flag combination that runs `agent-start.mjs`
passes through this one choke point.

One scoping note, not a defect: `AGENTS.md §1.3` permits `brahim` a **direct commit to `main`** for pure
bookkeeping (e.g. flipping a `blocked` row to `ready`), which never invokes `agent-start.mjs` at all. This
sits outside the guard's stated threat model — a forgotten `GH_TOKEN` producing a self-approving
`gh pr merge` under the box's default identity (the WHY block at `agent-start.mjs:132-137`) — since a
steward's direct commit has no PR/review step to self-approve and the steward's account is fixed. Not
raised as a finding; recorded so the next backward sweep doesn't have to re-derive it.
