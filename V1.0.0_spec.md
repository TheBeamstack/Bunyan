## 1. Vision & Guiding Principles

Build a browser-native, serverless-by-default authoring platform for building design that matches professional CAD/BIM tools (Revit, ArchiCAD) in geometric accuracy, while reaching that parity **progressively** rather than all at once.

Non-negotiable principles for every design decision in this document:

- **Exact geometry, always.** The source of truth for any shape is B-Rep solid geometry from the kernel — never a mesh. Meshes are a display artifact, regenerated on demand.
- **Additive, not disruptive, growth.** Every release from v1.0.0 onward must be able to add a new shape type, a new tool/action, or a new file format without modifying the core engine or breaking existing projects. This is the central architectural requirement — see Section 4.
- **MVP ≠ mini-Revit.** v1.0.0 does not replicate Revit's feature set. It must be genuinely usable for a real (if simple) building-design task, end to end, using a small, well-chosen set of primitives the extensibility model can grow from.
- **Free, open source, zero backend.** Static hosting on Cloudflare Pages. No accounts, no servers. **AGPL-3.0, dual-licensed with a commercial option** (decision D15, Section 11) — openness is a *product* decision, not a compliance detail: it is the wedge against Revit's lock-in.
- **Works offline after first load.** No network dependency is required to *use* the app once it has loaded once: a **service worker precaches the app shell and the WASM kernel** (Section 8), and all documents live locally (Section 7). First load necessarily downloads the app + kernel over the network; every subsequent use — including fully offline — is served from cache.
- **Agent-native by construction** *(decisions D19–D23, Section 4.6)*. An AI agent must be able to **explore, understand and operate Bunyan through instructions — with no SDK to install and no per-feature API wiring.** This is achieved not by building an agent integration, but by refusing to build a *second* API: **humans and agents act through the same Command layer**, the registries that generate the ribbon also generate the agent's tool list, and every command returns the state delta it produced so an action can be **verified**, not merely issued. **The UI has no private path to the kernel, and neither does an agent.** *Strategically this is the same wedge as openness (Section 11): "you will never lose access to your models, you can verify what the geometry engine does — and an agent can drive it out of the box, because there is one public API and it is the same one the buttons use."*
- **No architectural dead ends.** Nothing in v1.0.0 should have to be thrown away when v1.1.0 adds an optional multi-tenant backend and real-time collaboration. The domain model is designed against explicit long-term north-stars — see `core_logic.md`.

## 3. Process & Threading Architecture

```
Main thread                         Geometry Worker                  Optional: Macro Worker
─────────────                       ────────────────                 ──────────────────────
UI (React)                          OUR WASM KERNEL                  Pyodide (lazy-loaded,
Scene graph (three.js)     <──────    = our C++ ops                  only if macro panel
Command dispatcher          msg         + OCCT 7.9.3 (static)        is opened by the user —
Undo/redo stack             ────>   Command executor                 post-MVP, Section 10)
Persistence manager                 Persistent-naming resolver
Service worker (cache)              Tessellation (mesh + provenance)
                                    IFC read (IfcOpenShell → solids)
                                    Operation-failure marshaller
```

- **The WASM module *is* the kernel** (D14). JavaScript calls **our op set** — `makeBox`, `measure`, `tessellate`, `releaseShape`, … — not OCCT's API. Geometry logic lives in C++, inside the module. This is the opposite of `opencascade.js` (which exposes all of OCCT to JS and pays a boundary crossing per OCCT call), and it is what keeps the JS↔WASM surface small and stable however far the product grows: **new capability is a new C++ op, not more binding surface.**
- **Mesh buffers cross the boundary as zero-copy views, not element-by-element.** Reading an embind `std::vector` costs **one crossing per element** — ~1.8 M crossings for a 200k-vertex model, on every drag frame. The kernel hands JS `typed_memory_view`s instead (one crossing), which the TS adapter copies out synchronously. ⚠ Those views are invalidated by the next `tessellate` call.
- The geometry kernel **always** runs in a dedicated Web Worker, communicating via `postMessage` with transferable `ArrayBuffer`s. This keeps the UI thread responsive during expensive boolean/fillet operations regardless of model complexity.
- **v1.0.0 is single-threaded (D8).** Persistent naming (D1) is the project's #1 risk, and multi-threaded OCCT orders boolean output **non-deterministically**, which makes naming bugs far harder to reproduce. **Get correctness right on one core; chase speed in v1.0.x.** This also removes the cross-origin-isolation requirement entirely (Section 8).
- The kernel worker's public API is a **flat, versioned message protocol** (not a live object reference) so it can later be swapped, upgraded, or moved server-side in a future edition without touching the UI layer. This is the seam that keeps the future **headless/server-side kernel** north-star (`core_logic.md`) open.
- **Tessellation carries sub-shape provenance.** Every mesh buffer the worker emits includes a **provenance channel**: a per-triangle → face `SubShapeRef` map and per-edge-polyline → edge `SubShapeRef` map (Section 4.5). This is what makes viewport **sub-shape picking** (select a face/edge) able to return a stable `SubShapeRef` — the *input* side of the naming system. It is part of the frozen kernel protocol (Section 12).
- The persistent-naming resolver (Section 4.5) lives inside the geometry worker, alongside the kernel: it consumes the kernel's `Generated`/`Modified`/`IsDeleted` maker maps in TypeScript today, with a possible future C++ shim for performance. The worker protocol is kept engine-agnostic so that move requires no UI change.
- **Edit coalescing / interactivity budget.** Rapid parameter edits (e.g. dragging a slider or a handle) are **debounced and coalesced**, and an in-flight kernel operation superseded by a newer edit is **cancelled or its result discarded**. OCCT operations are not interruptible mid-call, so the dispatcher must drop stale results rather than block. Viewport camera manipulation never waits on the kernel.
- Pyodide (if/when the macro console is used) runs in its own worker, isolated from the modeling hot path, and is lazy-loaded only on first use so it never affects baseline load time.

## 4. Core Extensibility Architecture (the central requirement)

This section answers "the MVP must be 100% scalable through the 1.0.x line until it reaches Revit parity." **Five** registries/subsystems make this possible. Every future feature is an addition to one of these, never a change to the core. The full contracts and their interaction are documented in `architecture.md`; this section is the normative summary.

### 4.1 BIM Object Type Registry

Every modeled thing (wall, slab, door, column, eventually roof, curtain wall, stair, MEP run…) is a BIM Object Type implementing one shared contract:

```ts
interface BimObjectType<Params> {
  typeId: string;                       // e.g. "core.wall.v1"
  defaultParams(): Params;
  buildGeometry(params: Params, ctx: KernelContext): BuildResult; // calls the OCCT worker; may fail (Section 6.4)
  parameterSchema: ParamSchema;         // drives auto-generated property panel UI
  ifcMapping: IfcClassMapping;          // how this maps to/from IFC on import (export: v1.0.x)
  quantities?: QuantityMapping;         // typed quantities for future analysis/schedules (north-star)
  version: number;                      // for migrating saved projects as the type evolves
}
```

- New types are registered — the core scene graph, persistence format, and undo system never need the concrete list of types in advance.
- `version` + a per-type migration function keeps a v1.0.0 project file loadable after the Wall type gains new parameters in v1.0.4.
- `buildGeometry` returns a `BuildResult` (success with a `ShapeHandle`, or a typed failure — Section 6.4), never throwing across the worker boundary.
- The optional `quantities` field is declared now (a no-op consumer in v1.0.0) so the **analysis & quantities** north-star (`core_logic.md`) does not require a contract change later.
- MVP ships a small number of these (Section 5); everything after v1.0.0 is a new entry.

### 4.2 Command / Action Registry

Every action **any actor** can take — a human at the ribbon **or an AI agent** (Section 4.6, D19) — implements:

```ts
interface Command {
  commandId: string;                    // e.g. "core.createElement"
  argsSchema: ArgsSchema;               // ⟵ D21. Machine-readable, like a Type's parameterSchema.
                                        //    Generates BOTH the input UI and the AGENT'S TOOL DEFINITION.
  execute(ctx: DocumentContext, args: CommandArgs): CommandResult; // UndoableEdit on success; typed failure otherwise
  contributesUI?: RibbonContribution;   // optional: where it appears in the toolbar/ribbon
}
```

- The undo/redo stack operates purely on `UndoableEdit` objects, not command internals — adding commands never touches the undo system.
- **`execute` RETURNS the `UndoableEdit`** *(D23)*, it does not merely push it. The delta undo needs to *reverse* an action and the diff an actor needs to *verify* it are **the same object** — so verification is free, and an agent can check its own work.
- A command whose kernel work fails returns a **failure** and produces **no** `UndoableEdit` (Section 6.4). The failure is **typed** (one of the protocol's codes), i.e. machine-readable by an agent, not a stack trace.
- The ribbon/toolbar is **generated** from the registry, not hand-wired — a new command appears purely by registering it with a `contributesUI` descriptor.
- **The agent's tool list is generated from the SAME registry** *(D21)*: `argsSchema` is to an agent what `contributesUI` is to the ribbon. **One registry, three consumers** — ribbon, property panel, agent. A new command becomes an agent verb **with no way to forget**, because there is nowhere else for the truth to live.
- ⚠ **`DocumentContext` is the only holder of a `KernelClient`** (D19). No React component, and no agent, may call a kernel op directly (Section 4.6).

### 4.3 File Format Codec Registry

Import/export formats are registered as independent codecs against one interface (`Importer` / `Exporter`), decoupled from the BIM Object Type Registry via the `ifcMapping` field. Adding a format is additive.

- **v1.0.0 ships the IFC *importer*** (**IfcOpenShell → exact B-Rep solids**, decision D16) only; the IFC *exporter* is a sibling registration deferred to v1.0.x (Section 2, decision D3).
- The IFC codec's schema binding is abstracted (`IfcSchemaVersion`) so an IFC5/IFCX codec — and later STEP, DXF, glTF — are sibling registrations, not rewrites.

### 4.4 View / Representation Registry

3D view, 2D plan-cut view, 2D elevation, and (future) schedules/sheets are all "representations" of the same underlying document graph, registered independently, so 2D drafting and (north-star) quantity schedules can be added later without touching the 3D authoring core.

### 4.5 Persistent Naming Subsystem *(decision D1)*

**Problem.** When an `Opening` subtracts from a `Wall`, or a `fillet` is applied to an edge, that reference must survive a **rebuild** after the host's parameters change. OCCT booleans do **not** guarantee stable face/edge identity across regeneration. This is the "topological naming problem" that has historically plagued parametric CAD (e.g. FreeCAD). The validated decision is to solve it **from day 1** with a **functional (generative) naming** model rather than the a-posteriori geometric matching most open-source CAD relies on.

**Approach — functional / generative naming.**

- Identity is **assigned at creation and carried forward**, never recovered after the fact. A sub-shape's identity **is its derivation**: the operation that produced it plus the identities of the inputs that produced it (e.g. "the face generated by `Fillet(op#7)` acting on `Edge{generated by Extrude(op#3), role=lateral, k=2}`"). Because the identity is a structural path, it is immutable by construction.
- Propagation uses OCCT's `BRepBuilderAPI_MakeShape` maker interface — `Generated()` / `Modified()` / `IsDeleted()` — which is **core B-Rep** (no OCAF/TNaming dependency). Each operation labels its outputs from its inputs as it builds; there is **no geometric guessing on the resolve path**.
- **Division of labour between C++ and TypeScript** *(as built — `current_state.md` Entry 7)*. The kernel's C++ assigns **roles**: it answers *"which sub-shape is this, structurally?"* — a face's role comes from **the operation's own semantic accessors** (e.g. `BRepPrimAPI_MakeBox::BackFace()`), and an edge's role from **topology** (the canonical pair of the two faces that generate it — floating-point-free, and a bijection for a box). TypeScript answers *"whose is it?"*: it binds those roles to the owning DAG node and encodes the `SubShapeRef` token (`nodeId` + `role` + `occurrence`). **Geometry never enters the identity path in either half.**
- **⚠ The naming layer refuses what it cannot derive.** A sub-shape whose identity cannot be derived structurally (today: an edge not bounded by exactly two named faces) makes the operation **fail loudly** rather than invent an identity. A wrong-but-plausible name is far more expensive than a refusal, because it surfaces only much later — as an opening silently re-targeted onto a different wall.
- **⚠ A translation-table hazard, recorded because it already bit us.** Deriving a role from the operation still means *naming* what the operation returns, and the kernel's vocabulary is not ours. **OCCT's `LeftFace()` is the y-min face and its `FrontFace()` is x-max** — not what the names suggest. A first implementation mislabelled **four of a box's six faces**, and **every geometric check still passed**: the geometry was exact and only the *names* were wrong. The harness therefore **re-measures the role labels on every run** (Section 9.1). This is a check of *our labelling code* against geometry, which is **not** the same as deriving identity from geometry — the derivation is unchanged.
- Every sub-shape reference stored in `scene.json` is an **opaque, stable `SubShapeRef`** — a structured path (`nodeId` + `role` + `occurrence`) through the operation graph, never a raw OCCT index. `SubShapeRef` is an interface; its encoding may evolve within the `1.0.x` line via the same per-type/version migration mechanism as Section 4.1.
- **Hybrid graph granularity.** The operation graph is coarse-grained (feature-level) for the UI and model history, and fine-grained (primitive-op level) for internal topological propagation. References resolve against the fine layer; the user sees the coarse layer.

**⚠ OCCT history quality — SUPERSEDED BY MEASUREMENT, 2026-07-12 (decision D24, `current_state.md` Entry 9).**

> **The paragraph that stood here was a citation, not a measurement — and on OCCT 7.9.3 it is wrong.** It said, from the OCCT docs and the FreeCAD topological-naming literature, that `BRepBuilderAPI_MakeShape` history is *"robust for faces but weakest for edges and vertices generated by boolean section curves"*, and that the resolver's hardest case is chaining a fillet onto an edge produced by a boolean. **We measured it** (`tools/kernel-build/probe.cpp`, committed, re-runnable in ~60 s) rather than continuing to design around a fear. The results:

| Measured on OCCT 7.9.3 | Result |
|---|---|
| **Boolean history (cut through a wall; a circular penetration; a corner fuse)** | **COMPLETE.** Every output face, edge **and vertex** traces to an input. **Zero orphans.** Section edges appear in `Generated()` of **both** intersecting faces; section vertices in `Generated()` of the edges. **The literature's warning does not hold here.** |
| **The relation that is actually missing** | **Identity.** `Modified()` returns only the *splits* of a shape; a sub-shape the operation never touched is passed through as the **same** shape and appears in **no history list at all**. Read naively, that silence looks like *"unknown"*; it means *"unchanged"*. On a simple cut, **four of the wall's six faces** are accounted for by nothing else. |
| **The genuine weak spot** | **The FILLET, not the boolean.** `BRepFilletAPI_MakeFillet` reports its new face as `Generated` from the edge it rounds (exactly what naming needs) but **rebuilds the surrounding edges and vertices as new objects with no history**: 4 edges + 4 vertices lost on a box; 6 + 4 on the boolean case. |
| **The spec's "hardest case" (fillet on a boolean-made edge)** | **Fully nameable.** 23/29 edges from history, 4 from the face pair, **2 from the endpoint tie-break** — and 0 refused. |
| **The sanctioned positional key** (centroid, below) | **NOT NEEDED in any of the six cases.** No geometry entered the identity path. |
| **⚠ TRANSFORM — rotate, mirror, and a rotate of a wall that already has an opening** *(measured 2026-07-13, Entry 11; probe cases 7-10)* | **A topological ISOMORPHISM.** 100% of output faces AND edges accounted for through history, **1:1, zero orphans**, in both copy modes and for a **mirror** (a negative, handedness-flipping transform, whose solid comes back with **positive** volume). ⇒ `transform` is **pure INHERIT**: it creates **no identities**, and a rotated wall is the **same wall**. |
| **⚠⚠ THE SPLIT FACE — a groove across a wall** *(measured 2026-07-13, Entry 11; probe case 6b)* | **The hole Entry 9 left.** Two faces, one identical derivation — and the kernel **refused**, so a wall with a **chase** in it could not be modelled. **They differ by ADJACENCY** (the lower half touches `z-min`, the upper `z-max`), which is pure topology. Faces now carry the same structural tie-break the edges always had. **See the ⚠⚠ block below.** |
| **⚠ REVOLVE — a full 360° turn** *(measured 2026-07-13, Entry 14; probe cases 12-15)* | **Three surprises, none of them in the literature, and the last one nearly fatal.** (1) A full revolve has **no caps** — and `FirstShape()`/`LastShape()` do **not** return null for it; they return a face that is **not in the result**, so a prism-style cap check refuses every column. (2) Each lateral face **closes on itself**: its seam edge **IS the authored profile edge**, returned by *identity* — so unlike the cylinder, the seam needs no accessor. (3) **⚠ A segment PERPENDICULAR to the axis reports NO HISTORY AT ALL** (`Generated()` empty, `IsDeleted()` true) **while its face sits in the result** — that face is the flat bottom of every column and the base of every dome. It is named from **the circles its segment's endpoint vertices sweep** (pure topology), and the same test distinguishes it from a segment lying *on* the axis, which sweeps no circle and correctly has no face. |
| **⚠⚠ THE GENUINELY SYMMETRIC TIE — HIT AT LAST, and by an ordinary shape** *(measured 2026-07-13, Entry 14; probe case 11b)* | **A duct drilled CLEAN THROUGH a ROUND column.** Every boolean this project ever tested cut a **box**, where a duct enters via `y-min` and leaves via `y-max` — two faces, two derivations, nothing to disambiguate. **A round column has ONE lateral face that wraps all the way around**, so the duct enters and leaves through **the same face**: both rims share a derivation, bound the same two faces, and have endpoint signatures that are identical. **No structural rule can separate them.** The kernel **refuses**, loudly and correctly — but a service penetration through a circular column is not exotic, it is Tuesday. ⇒ **This is the signal this section reserved the positional key for. See the ⚠⚠⚠ block below — it is an OWNER DECISION.** |

**⇒ The resolver (implemented, `packages/kernel-occt/src/naming.ts` + `tools/kernel-build/src/kernel.cpp`).** Every output sub-shape is accounted for by exactly one of four relations, tried in order; if none applies the **operation fails**:

| Relation | Meaning |
|---|---|
| **PRIMITIVE** | The operation names it from its **own semantic accessors** (`MakeBox::BackFace()`, `BRepPrim_Cylinder::LateralFace()`). Primitives have no ancestors, so nothing else could. |
| **INHERIT** | One ancestor **of the same kind**, and this is its only output ⇒ it **IS** that sub-shape still, and **keeps its token verbatim**. ⚠ **This is the relation that makes BIM work:** cutting a window leaves the wall's front face `Modified` but still *one* face, so it stays `wall-1/face/y-min#0` and a window already hosted on it is **not re-targeted**. It also covers the pass-through case OCCT reports nowhere. |
| **DERIVE** | It has ancestors but is none of them — a **split**, a coplanar **merge**, or a wholly new sub-shape **generated** by them (a section curve; a fillet's face). Named as *the operation applied to its canonically-sorted ancestors*, plus an occurrence index. ⚠ **The occurrence index is assigned by a structural tie-break, never by traversal order** — see *"Splits"* below, and the ⚠ note under it. |
| **ADJACENT** | No history, and not a pass-through — OCCT rebuilt it (the fillet). An edge is named by **the pair of faces bounding it**; those faces are named, so the name stays structural and FP-free. If two edges share a face pair, the **endpoint vertices** (themselves named by the faces meeting at them) break the tie. |

**⚠⚠ THE SPLIT FACE — a hole in the above, found 2026-07-13 (Entry 11) and now closed. Read this before touching the resolver.**

> The four relations were shipped in Entry 9 with the *edges* given a structural tie-break (their endpoint signature) and the *faces* given **none**. Faces with an identical derivation were simply **refused**. Entry 9's probe never produced such a case, so the gap was invisible.
>
> **It is trivially reachable, and by an utterly ordinary BIM operation.** A **groove across a wall** — a chase, a rebate, a shadow gap, a recessed band — **splits the wall's front face into two.** Both halves derive from the same parent face, by the same relation, from the same operand. History cannot separate them. **So the kernel refused: a wall with a chase in it could not be modelled at all.**
>
> **The halves are not indistinguishable — they touch DIFFERENT faces.** MEASURED (`probe.cpp` case 6b, the `touches` field): the half below the groove meets the wall's `z-min` face; the half above meets `z-max`. That is **pure topology** — no coordinate, no tolerance, nothing that drifts when the wall is resized or the groove is moved.
>
> **⇒ Faces now get exactly the tie-break the edges always had:** sort by derivation, then by a **structural signature** (the *derivations of the neighbouring faces*); assign the occurrence index in that order; and **refuse only when derivation AND signature are both identical.** This is not a new rule — **it is the rule this section already required** (*"children are ordered by a structural tie-break"*, below); it had simply never been implemented for faces.
>
> **The refusal that remains is the genuinely symmetric split** (same parent, same neighbours) — and *that* is the case the positional key was always reserved for. It is **still not implemented**, still on purpose.

- **The seam.** A full cylinder's lateral face closes on itself, so its seam edge is bounded by **one** face twice — no face *pair* exists. Only the operation can name it, and it does (`lateral.seam`). ⚠ **This, not the boolean, is the first wall the old kernel hit:** it refused to build a cylinder at all.
- **v1.0.0 still constrains itself to operations whose coverage is verified** (the naming regression suite, Section 9, is the gate). An operation whose history is inadequate is wrapped or deferred — it does **not** silently fall back to geometric guessing.
**⚠⚠⚠ THE SIGNAL HAS FIRED. A REAL MODEL HAS HIT THE GENUINELY SYMMETRIC TIE — 2026-07-13, Entry 14. THIS IS NOW AN OWNER DECISION, AND IT IS THE ONE OPEN QUESTION IN THE NAMING DESIGN.**

> The line below says: *"If a real model ever hits a genuinely symmetric tie, that refusal is the signal to implement the key **deliberately**."* **It has.**
>
> **A duct drilled clean through a ROUND column.** Not a contrived shape — a service penetration through a circular column, which every building has. Measured (`probe.cpp`, case `cut_round_column_by_duct`): the column's lateral face **wraps all the way around**, so the duct enters and leaves through **the same face**. The two rims are `Generated` by **the same face pair**, bound **the same two faces**, and their endpoints carry **the same signature**. Where the groove's two halves touched *different* faces (Entry 11's structural rescue), these two rims touch *nothing that differs*. **They are topologically indistinguishable.** No adjacency rule, no endpoint rule, no neighbour signature reaches them.
>
> ⚠ **It has NOTHING to do with `revolve`, and predates it.** The identical failure occurs on a plain `makeCylinder` column and has been reachable since **Entry 9**. It went unseen for five entries because **every boolean ever tested cut a box** — where the duct enters via `y-min` and leaves via `y-max`, two different faces, two different derivations, no tie to break. It surfaced only when a revolve test cut a *round* column, which is the third time this project has learned the same lesson: **the probe only measures the shapes you think to cut.**
>
> **Today the kernel REFUSES it** — loudly, with `UNRESOLVED_SUBSHAPE_REF`, and that is the correct behaviour under this section as written (predictable breakage beats silent wrongness). Nothing is broken, and no wrong name has ever been assigned. **But a whole class of ordinary modelling is unavailable**, and it will not fix itself.
>
> **The decision is the Architect's, because implementing the key puts GEOMETRY ON THE IDENTITY PATH** — the single invariant the entire product rests on (D1/D18). It is not a refactor an agent may take on its own initiative. The options, and their costs, are in `current_state.md` §5 task 1. **A test pins the refusal** (`tests/naming-revolve.test.ts`, *"KNOWN LIMITATION"*), so it is visible in CI rather than folklore, and it flips the day the key lands.

- **The `centroid` positional key below remains the sole sanctioned last resort — and is STILL NOT IMPLEMENTED, but no longer because nothing has needed it.** It is unimplemented because **the case that needs it has now appeared and the ruling has not been made** (the block above). Shipping an untested geometric rule on the identity path where it could fire by accident is still the thing to avoid; the resolver **refuses** instead, with `UNRESOLVED_SUBSHAPE_REF`.
  - ⚠ **The prime suspect was the MIRROR, and it was acquitted — by measurement** (Entry 11). A mirror is a **topological isomorphism**: every face maps to exactly one face, so `transform` is **pure INHERIT** and creates no identities at all. It cannot produce a symmetric tie. **The case that actually got close was the split face** (a groove), and that is separated **structurally**, by adjacency — see the ⚠⚠ block above.
  - ⚠ **And the real one, when it came, was neither.** It was not a face at all: it is **two EDGES** — the rims of a hole drilled through a round column — with the same derivation, the same bounding faces and the same endpoint signature. **The shape of the case was mis-predicted twice** (first the mirror, then "two faces with the same parent and neighbours"). Both guesses were wrong, and the measurement was right. *Do not predict the third one; cut the shape and look.*
  - ⚠ **The one way to force a genuine collision is to ask an incoherent question:** fusing a shape with a **transform of itself**. Both operands then carry identical tokens, and two different faces resolve to one identity. The kernel **refuses**. That is correct — an element instance is in **one** place; a mirrored copy of a wall is a **second wall**, a new element with its own `nodeId`, which the document layer creates and transforms (P3). Given distinct `nodeId`s there is no collision and never was.
- **The fallback contract**, if the general resolver ever proves too costly: constrain the *very first* internal milestone to purely positional openings and non-persisted fillets, but ship v1.0.0 only once `SubShapeRef` is real — retrofitting it later would break `scene.json` and violate the "no dead ends" principle. *(This contract is now unlikely to be needed: the resolver is built and green.)*

**Splits, merges, and determinism.**

- When a parameter change makes one sub-shape split into many (or merge), the maker interface returns a 1→N (or N→1) map. Children are ordered by a **structural tie-break**: the identities of the tool/input entities that caused the split (pure graph data, no geometry). Each operation type defines its ordering rule. **⚠ AS BUILT (Entry 11):** an **edge**'s tie-break is its **endpoint signature** (the faces meeting at each end); a **face**'s is its **neighbour signature** (the derivations of the faces it touches). *Faces went un-tie-broken from Entry 9 until Entry 11 — the rule was specified here and simply not implemented, and a groove across a wall was unmodellable for it. If you add a sub-shape kind, give it a tie-break.*
- For a **genuinely symmetric** split where structural data cannot break the tie, a single **bounded positional key** (centroid rounded to the mm grid, lexicographic) is the *sole* sanctioned last resort — the only place geometry touches the resolve path. See Section 6.5 for the cross-machine determinism rules this key must obey. **⚠ This line has now guessed the shape of that case WRONG TWICE, and been corrected by measurement both times.** It first said *"e.g. mirrored openings"* — wrong: a mirror is an isomorphism and cannot tie. It then said *"two faces with the same parent and the same neighbours"* — also wrong. **The real case, measured 2026-07-13 (Entry 14), is two EDGES: the rims of a duct drilled through a ROUND column**, which share a derivation, share both bounding faces, and have identical endpoint signatures. **⇒ It is HIT, it is ordinary, and the ruling is owed — see the ⚠⚠⚠ block above.**
- Each operation's `Generated`/`Modified` output is passed through a **canonical re-sort** (the structural tie-break above) **before** IDs are assigned, so **the kernel's traversal order can never leak into a name**. *(Rewritten 2026-07-12: this rule was originally justified by multi-threaded boolean non-determinism. **v1.0.0 is single-threaded (D8), so that justification no longer applies today — but the re-sort remains a hard requirement**, both because OCCT's single-threaded traversal order is still not something identity may depend on, and because it is the precondition for turning multi-threading on in v1.0.x without invalidating a single saved file. It is implemented.)*

**Rebuild, load, and broken references.**

- The identity **token map** is persisted in `scene.json`. On an edit, only the affected subgraph is rebuilt and identities are re-propagated (incremental rebuild). On load, deterministic replay re-binds the stored tokens to concrete OCCT entities.
- On rebuild, each `SubShapeRef` is re-resolved along its derivation path. If a reference becomes **unresolvable** (the host was edited so the referenced sub-shape no longer exists), the dependent feature is marked **broken** and surfaced in the UI for **manual retargeting** — it is **never** silently reattached to a different element.

**Risk (recorded honestly).** This remains the single hardest engineering item in v1.0.0 and can dominate the timeline. It is on the critical path for parametric `Opening` and `fillet`/`chamfer`. It is materially de-risked versus the draft by depending only on the **core maker interface** (no unverified OCAF/TNaming binding) — but the edge/vertex-history caveat above is the residual risk to watch.

**Why this matters concretely:** shipping "add a Door type" or "add a Fillet command" in v1.0.3 should be an additive PR against a registry — not a cross-cutting change. This is what keeps parallel work conflict-free in the core.

### 4.6 The Agent Surface — *the command layer is the API* **(decisions D19–D23, owner rulings 2026-07-12)**

**The requirement, in the owner's words:** an AI agent (Claude, or any LLM-based agent) should be able to **explore, understand and operate the app through instructions — with no complex setup: no heavy SDK install, no manual API wiring per feature.**

**The design answer is not to build an agent integration. It is to refuse to build a second API.**

#### 4.6.1 D19 — One command layer. No actor bypasses it.

```
  human (button / drag) ─┐
  agent (window.bunyan) ─├──►  COMMAND REGISTRY (§4.2)  ──►  DocumentContext  ──►  KernelClient ──► OCCT
  MCP bridge [v1.0.x]  ──┘          the only door
```

Every action, from every actor, is a Command. **The UI gets no private channel to the geometry kernel, and neither does an agent.**

> ⚠ **Why "no exceptions" is not pedantry.** A "quick path" from the UI straight to the kernel (for a drag preview, say) is always tempting and always corrosive: **every capability reachable only through the UI is a capability the agent can never have** — and nobody notices the gap until an agent is asked to use it, by which time the two surfaces have diverged for a year. **If the UI can do it, a Command expresses it. If no Command expresses it, the UI cannot do it.**

**⚠ Two layers exist, and only one of them is the agent's.** Confusing them is the expensive mistake available here:

| | **Kernel ops** (`@bunyan/protocol`) | **Document commands** (§4.2) |
|---|---|---|
| Vocabulary | `makeBox`, `tessellate`, `measure` | `createElement`, `setProperty`, `deleteElement`, `queryElements` |
| Level | geometry primitives | BIM semantics |
| Freezes | **end of P3** (D13) | **P5**, after Wall + Opening (D13) |
| Who may call it | **`DocumentContext` only** | **every actor** |

An agent calling a kernel op directly would produce a solid that **no entity owns, no undo can remove, and no `SubShapeRef` names.** The kernel is not an API surface; it is an *implementation* of one.

#### 4.6.2 D20 — Granularity: type-driven verbs; primitives as the escape hatch

The primary verb is **`createElement(typeId, params)`** — *"create a `core.wall.v1`, 4000 mm long, 2500 mm high"* — **not** *"draw a rectangle, then extrude it 2500 mm"*.

This costs nothing, because **a BIM Object Type already *is* the recipe from parameters to geometry** (§4.1). The parametric type registry makes semantic verbs the *natural default*; the sketch-level primitives of §5.2 remain, as the **GenericSolid** escape hatch (§5.1) rather than the main road.

**Composite verbs** ("add a room" = 4 walls + a slab + a door, atomically) are **deferred to v1.0.x** — they require transaction grouping, for which the contract now **reserves room** (D23).

#### 4.6.3 D21 — Capability discovery: generated from the registries, never hand-maintained

The capability endpoint is a **derived projection of the registries.** The registries are already the **only** place a Type or a Command can be declared (§4: *"the core never hard-codes the concrete lists"*) — so a schema generated from them **cannot** drift out of date. **A hand-written agent document certainly would**, and within weeks.

⇒ `Command` gains **`argsSchema`** (§4.2), exactly as `BimObjectType` already carries `parameterSchema`. **An agent needs no external documentation — it asks the app.**

#### 4.6.4 D22 — Transport: `window.bunyan` first. MCP deferred, not rejected.

| | **`window.bunyan` [v1.0.0]** | **MCP bridge [v1.0.x]** |
|---|---|---|
| What it is | the Command layer, exposed on the page | a small **local program** relaying an *external* agent (Claude Desktop / Claude Code) into the browser |
| Serves | an **in-browser** agent (e.g. Claude in Chrome) | agents outside the browser |
| Install cost | **ZERO — it ships with the app** | a download + a config file + a running process |
| Backend | **none** | a local process and a port |

**`window.bunyan` is built first because "no complex setup" is a hard requirement, and an MCP bridge *is* that setup.** It would also puncture the property that defines v1.0.0 — **client-only, zero backend, designs never leave the device** (§1). **MCP is deferred, not rejected**, and it is cheap later *precisely because of D19*: an MCP server is **another transport over the same verb set**, not a second API. (The same move the kernel seam already makes: `Transport` is swappable, and `WorkerTransport`/`InProcessTransport` prove it.)

```ts
window.bunyan = {
  version:      () => ({ agentApi: 1, protocol: 1, kernelBuildId, app }),
  listCommands: () => CommandDescriptor[],  // GENERATED from the Command registry (argsSchema)
  listTypes:    () => TypeDescriptor[],     // GENERATED from the BIM Object Type registry
  execute:      (commandId, args) => CommandResult,  // → UndoableEdit (the diff) | typed failure
  query:        (q) => SemanticView,        // the recipe — ids/types/params/relations, NOT triangles
};
```

**Versioned separately (D22).** The surface carries its own **`agentApi` version**, independent of `protocolVersion` (the kernel) and of the P5 type-contract freeze (D13) — so agent ergonomics may improve **without amending a frozen contract**. An agent asks what it is talking to, and adapts.

#### 4.6.5 D23 — Explore, act, verify

- **Read/query, two tiers.** **Document-level** queries (`getSceneGraph`, `getElementById`, filter by type/level/property) read the **parametric recipe**, which *is* the truth (§1) — **they need no kernel op at all.** **Geometric** queries (tight bounds, spatial proximity/containment) need the B-Rep, so they are **kernel ops, added before the protocol freezes at the end of P3** (adding an op is one line in `OpMap` today; a contract amendment afterwards).
- ⚠ **A query API returns SEMANTICS, not triangles.** A `Float32Array` of 200 k vertices is unreadable to an agent. The agent reads a **semantic Representation** (§4.4) — ids, types, params, levels, quantities, relationships. *The 3D view is the projection for eyes; this is the projection for reasoning. Both are derived; neither is truth.*
- **Every command returns its diff.** `execute` returns the `UndoableEdit` (§4.2). With the exact **`measure`** op (D17 — B-Rep truth, never the mesh) and typed failures (§6.4), an agent has a **closed verification loop: act → read the diff → measure the result.** Most CAD tools cannot tell a caller what an edit actually did.
- **Transactions reserved.** `UndoableEdit` carries a **transaction id**; edits sharing one undo/redo as a **single all-or-nothing unit**. **v1.0.0 emits one edit per command** (each its own transaction) — but the field exists **now**, because retrofitting grouping into a frozen undo contract is invasive and every composite verb will need it (§6.1).
- ⚠ **Agent commands opt OUT of edit-coalescing.** The dispatcher supersedes an in-flight request when a newer one shares its `coalesceKey` (§3) — right for a human dragging a slider, **wrong** for an agent, which issued one deliberate command and would get a `SUPERSEDED` failure that is meaningless in its context. **Coalescing is a property of interactive input, not of commands.**

#### 4.6.6 What this already gets for free (and why it was cheap)

The rulings above were affordable because **the document model, the registries and the command layer had not been written yet** — this is a greenfield decision on the one unbuilt layer, not a retrofit. Four things were *already* in place and simply had to be pointed at the agent:

1. **The renderer was already decoupled** — the kernel is a pure function that knows nothing of the DOM (which is why 62 tests run headlessly). There was no model/view entanglement to unwind, because there is no view yet.
2. **Registries were already the only way to add a type or command**, and were already required to *generate* the UI. Generating an agent tool list is the same mechanism, aimed one step further.
3. **`UndoableEdit` was already a state delta, not a command replay** (D-fold). A delta *is* a diff.
4. **Identity was already stable *below* the entity level** (`SubShapeRef`, §4.5). An agent can say *"a window on the south face of that wall"* and the reference **survives the wall being resized** — the thing most CAD tools cannot promise, and the thing that makes agent-authored parametric edits trustworthy rather than merely possible.

**⚠ Trust boundary.** `window.bunyan` is a **page-global** API — any script in the tab can drive the model. Acceptable in v1.0.0 (no backend, no account, no secret, the user's own tab), and it is **not** a privilege escalation: it exposes exactly what the ribbon exposes, which is the point of D19. It becomes a **real boundary** the moment the page runs code Bunyan did not author — the **Pyodide macro console** (§10) or any plugin surface. **That code must go through the same Command layer, and its capability grant must be decided before it ships, not after** (architecture §10).

**⚠ An agent cannot silently save to a file.** The File System Access API needs a **user gesture** to re-grant write permission after a reload (§7). An agent can author the entire model; **a human still clicks to save**. Autosave to OPFS/IndexedDB is unaffected, so agent work is never *lost* — it is just never written to the user's file without them.

### 5.2 Actions (v1.0.0)

**Every action below is a Command (§4.2), and therefore automatically an agent verb (§4.6) — there is no separate agent feature list, and there never will be.** The *primary* authoring verbs are type-driven (D20) — `createElement` / `setProperty` / `deleteElement` / `queryElements` against the BIM Object Type registry — and the sketch-level primitives below are the **GenericSolid escape hatch**, not the main road.

- **2D sketching:** line, rectangle, circle, arc, dimension entry (numeric input, **not** full geometric constraint solving yet). Sketches are **validated** (closed, non-self-intersecting) before being handed to extrude/revolve.
- **Extrude**, **boolean** (union/subtract/intersect), **fillet/chamfer** edge (persisted via `SubShapeRef`).
- **Move, rotate, copy, array** (linear/grid).
- **Level management**, object-to-level assignment.
- **Section-cut-based 2D views** — a plan view **and one elevation** — generated from the 3D model as real cuts of the real geometry (itself a proof that the kernel is the source of truth), **not** a separate drafting engine.
- **IFC import** (mapped-or-GenericSolid). *IFC export is v1.0.x.*
- **Save / Open** (local `.bimproj`, Section 7).

### 5.3 Explicit non-goals for v1.0.0

Deferred to later 1.0.x releases (all additive registry entries — none require a v1.0.0 redesign): **multi-threaded OCCT** (decision D8 — v1.0.0 is single-threaded, and the canonical re-sort in 4.5 is what keeps that door open); **IFC export & embedded-IFC-on-save** (decision D3); geometry **auto-repair** of failed operations (Section 6.4); a real geometric **constraint solver**; curtain walls; roofs beyond a flat/single-slope slab; stairs/railings as parametric families; MEP routing; schedules/quantities; sheet/print layout; rendering materials/lighting beyond basic shading; the Pyodide **macro console**; multi-user real-time co-editing; cloud storage; code-compliance checking.

## 6. Data Model & File Format

Project files are a single `.bimproj` package (a zip), so "save locally, re-import later" works with zero backend:

```
project.bimproj (zip)
├── manifest.json         # app version, schema version, KERNEL BUILD ID (occt-7.9.3-emcc-6.0.2),
│                         #   list of BIM object type versions used
├── scene.json            # parametric object graph + persisted naming token map:
│                         #   {id, typeId, params, levelId, transform, subShapeRefs[]}
│                         #   plus the operation-DAG identity tokens (Section 4.5)
├── geometry-cache.brep   # OCCT-native cached B-Rep, to avoid full rebuild on load
├── history.json          # command/undo history (optional, for session continuity)
└── thumbnail.png         # generated on save from the active 3D view (Section 6.6)
                          # (v1.0.x adds export.ifc — deferred, decision D3)
```

- **Units & precision.** All geometry is authored and stored in **millimeters** (project internal unit), double precision. IFC declares the corresponding `IfcSIUnit` (`MILLI`, `METRE`); the mm grid is also the rounding basis for the Section 4.5 positional last-resort tie-break. Large-coordinate robustness is addressed in Section 6.5.
- `scene.json` is the **editable parametric truth**; `geometry-cache.brep` is a performance cache, rebuildable from `scene.json` if missing or stale (a corrupted cache never loses the actual design).
- `manifest.json`'s per-type version list drives the Section 4.1 migration mechanism on load. The recorded **kernel build id** — `occt-<occt-version>-emcc-<emcc-version>`, e.g. `occt-7.9.3-emcc-6.0.2` — guards BREP-cache compatibility: if the loading app's kernel build differs, the cache is treated as stale and rebuilt. It changes only when OCCT or the toolchain moves, so it is stable across ordinary releases.
- `scene.json` sub-shape references are opaque `SubShapeRef`s (Section 4.5), never raw OCCT indices.

### 6.1 Undo/redo semantics (decision D-fold)

The undo stack is a stack of `UndoableEdit` **state deltas**, not a blind command replay. Because sub-shape references are stable (`SubShapeRef`) and geometry is deterministically rebuildable from `scene.json`, undo restores the prior parametric state and re-resolves references, avoiding the "replay + nondeterministic boolean topology" hazard. Undo/redo may therefore trigger an incremental kernel rebuild of the affected subgraph (not O(1)); it participates in the same edit-coalescing budget as Section 3. `history.json` persists this stack for session continuity only; it is optional and never the source of truth. Manual retargeting of a broken reference (Section 4.5) is itself an `UndoableEdit`.

**Two properties added by D23 (Section 4.6), both load-bearing for the agent surface:**

- **The delta is returned, not just pushed.** `Command.execute` **returns** its `UndoableEdit`. The state delta undo needs in order to *reverse* an action and the diff an actor needs in order to *verify* it are **the same object** — so verification costs nothing extra, and an agent (or a test, or a future co-editing peer) can check what an edit actually did rather than assume.
- **Transaction grouping is RESERVED, not built.** An `UndoableEdit` carries an optional **transaction id**; edits sharing one undo and redo as **a single all-or-nothing unit**. **v1.0.0 emits exactly one edit per command** (every edit is its own transaction) — the mechanism is *not* implemented. The **field and the semantics are fixed now** because the undo contract freezes at P5 (D13), retrofitting grouping into a frozen contract is invasive, and **every composite verb the product grows toward** ("add a room", "import and place") is a set of edits that must never be left half-applied.

### 6.2 `ShapeHandle` lifecycle & WASM memory management *(new 2026-07-08)*

OCCT objects live on the Emscripten heap and are **not** garbage-collected by JS — each `TopoDS_Shape` and intermediate must be explicitly released. Left unmanaged, a long editing session leaks WASM memory until the tab OOMs. Normative rules:

- A `ShapeHandle` is an opaque token owned by the worker; the main thread never holds raw OCCT pointers.
- The worker maintains an explicit **handle registry** with deterministic ownership: handles referenced by the live document graph or the persisted BREP cache are retained; all intermediates from a rebuild are freed at the end of that rebuild.
- Superseded geometry from a coalesced/cancelled edit (Section 3) is freed when its result is discarded.
- The worker exposes heap-usage telemetry to the app so a soft budget can warn before exhaustion (Section 8).

### 6.3 (reserved)

### 6.4 Operation-failure contract *(new 2026-07-08, decision D10)*

OCCT operations fail routinely on legitimate user input — a fillet radius larger than the adjacent geometry, a self-intersecting or open profile, a boolean that yields an empty/invalid shape, or an internal `Standard_Failure`. v1.0.0 behavior is specified, not left to chance:

- **Safe marshalling.** The worker wraps every kernel call so an OCCT C++ exception (`Standard_Failure`) or an invalid-result check is caught and returned as a **structured, typed failure** across the message protocol — it never crashes the WASM instance or the tab.
- **Reject + keep last-good.** A failed operation produces **no** `UndoableEdit`; the document remains at its last valid state. The user sees a typed, dismissible error explaining what failed (e.g. "fillet radius too large for edge").
- **No silent geometry.** v1.0.0 does **not** attempt auto-repair (`ShapeFix`, tolerance relaxation, retry). Auto-repair is a **flagged v1.0.x** refinement, as is a **downloadable repro bundle** (`scene.json` + the failing op) for field diagnostics — both are recorded as deferred work items here so they are not forgotten (there is no backend telemetry channel, so the repro bundle is the intended field-diagnostics path).

### 6.5 Cross-machine & large-coordinate determinism *(new 2026-07-08)*

The two build actors run different OCCT builds on different hardware (Section 12), and CI checks values seeded elsewhere. Determinism rules:

- **Structural IDs are floating-point-free.** The adjacency-graph hash (Section 9) is computed over structural `SubShapeRef` strings, so it is reproducible across machines by construction.
- **The positional tie-break is the only FP-sensitive identity path.** Its mm-grid rounding must use a fixed rounding mode and a grid coarse enough that legitimately distinct symmetric sub-shapes never collide; the golden-seeding environment is **pinned** (documented OCCT build + platform) so the seeded keys are reproducible. If two distinct sub-shapes round to the same key, that is a modelling-determinism defect surfaced by the naming regression suite, not silently tolerated.
- **Large coordinates.** Buildings modelled in mm produce large coordinate magnitudes (a 100 m span = 100 000 mm) against OCCT's default linear tolerance, which can stress boolean robustness for fine (mm-scale) features on large models. v1.0.0 documents a working-precision policy and the naming/golden suites include at least one large-extent model to catch regressions.

### 6.6 Thumbnails

`thumbnail.png` is generated on explicit save by rendering the active 3D view offscreen at a fixed small resolution; it is a convenience artifact only and never affects load.

## 7. Persistence Architecture (no backend)

| Mechanism | Purpose | Browser support |
|---|---|---|
| **File System Access API** (`showSaveFilePicker`/`createWritable`) | Primary Save / Save As to a real local file, with a stored handle for silent re-save **within the same session** | Chrome/Edge (Chromium) |
| **Zip-blob download + `<input type=file>` import** | Universal fallback Save As / Open, works everywhere | All browsers |
| **OPFS** (Origin Private File System) | Fast local scratch storage for the geometry cache during a session | All modern browsers |
| **IndexedDB** | Autosave snapshots, undo-history persistence, app settings, stored file handles | All modern browsers |
| **Service Worker Cache Storage** | Offline precache of app shell + WASM kernel (Section 8) | All modern browsers |

- **Save-handle permission reality (2026-07-08 correction).** A stored File System Access handle allows silent re-save **within a session**. **After a page reload the browser requires a user gesture to re-grant write permission** (`queryPermission`/`requestPermission` return `prompt`). The UX is therefore a one-click "resume saving to *file*" affordance on the next session, not truly silent cross-session writes. The universal download/upload fallback has no such restriction but is not silent.
- **Autosave.** Autosave writes a lightweight snapshot — `scene.json` + `geometry-cache.brep` only — to OPFS/IndexedDB on an interval **and** after every *N* undoable edits, independent of whether an explicit save file is open. Snapshots are kept as a **capped ring** (the most recent ~5, oldest dropped), and the app requests `navigator.storage.persist()` so this crash-recovery layer resists browser eviction.

## 8. Deployment, Offline & Load Budget

> **⚠ REWRITTEN 2026-07-12 (decision D8 — single-threaded).** This section previously required cross-origin isolation (`COOP`/`COEP`), `SharedArrayBuffer`, **two** WASM artifacts, and boot-time capability detection to choose between them. **All of that is gone.** Shipping single-threaded is not only a naming-determinism decision — it is a large deployment simplification, and it *widens* where the app can run: cross-origin-isolated pages cannot embed non-CORP resources, and `SharedArrayBuffer` is blocked outright in some embedded/enterprise contexts. Bunyan now has **no such constraints**.

- **Cloudflare Pages**, static output only, for v1.0.0.
- **No COOP/COEP headers. No `SharedArrayBuffer`. No capability detection. ONE WASM artifact.** The kernel is single-threaded (D8), so none of it is needed. *(When multi-threading lands in v1.0.x, the headers, the second artifact and the detection all come back — Section 13. The `_headers` mechanism is therefore designed for, but not used by, v1.0.0.)*
- WASM assets served with correct `application/wasm` MIME type (Cloudflare Pages default) and preloaded/streamed to minimize first-load latency.
- **Offline & PWA (D11).** A **service worker** precaches the app shell and the WASM kernel, keyed by the **kernel build id** (`occt-<occt-version>-emcc-<emcc-version>`, Section 6) so a new release invalidates the cache atomically; a **Web App Manifest** makes the app installable. This backs the Section 1 "works offline after first load" principle. **One artifact to cache.**
- **First-load & size budget.** v1.0.0 sets an explicit **first-load size and time budget** (measured in CI on a throttled profile), met with streaming compilation, preloading and code-splitting. Exceeding it blocks release (Section 9).

  **⚠ Current kernel: 14.53 MB raw / 4.22 MB gzip** *(2026-07-13, Entry 12 — `extrude` + `chamfer` added ~0.09 MB gzip, negligible)* — **up from 3.98 MB / 1.47 MB**, because the kernel now reaches OCCT's boolean, fillet, extrema and solid-classifier code (`TKBO`, `TKBool`, `TKFillet`, `TKPrim`). **That 2.8× on the wire is the price of the ops that make it a modeller rather than a box viewer**, and it is mostly irreducible: `-Os` was measured and saves only 1.5% gzip (4.07 MB), so the build stays on `-O2`. Still **3× smaller over the wire than `opencascade.js`** (13.1 MB gzip), because the linker keeps only the OCCT code our ops actually reach (D14).

  **⇒ OPEN, and it needs an owner call before P4 (§13):** 4.22 MB gzip is a real first-load cost on a slow connection. The levers, cheapest first: **(a)** accept it — the service worker caches it once and the app is then offline-first (D11), so the cost is paid on first visit only; **(b)** **lazy-load the kernel** behind the app shell, so the UI paints before the WASM arrives; **(c)** split the kernel into a core module + a booleans/fillet module fetched on first use — real work, and it re-opens the dead-stripping question. **No decision is needed to continue P2/P3**; it is recorded here so it is not discovered under release pressure.

## 9. Quality & Testing Strategy

### 9.0 Scope of verification *(decision D9, rewritten 2026-07-11)*

**We trust OCCT. We verify our own code.**

OCCT is an industrial B-Rep kernel with decades of production use. Validating *it* is not Bunyan's job, is not achievable within this project, and would require a second, genuinely independent geometry kernel that we are not going to build or adopt. Every check in this section exists to catch **our** errors:

- a **mis-wired parameter** (we built a 200 mm wall where we meant 2000);
- an **operation applied wrongly** (wrong primitive, wrong order, wrong input shape);
- a **broken or mis-configured WASM build** (our OCCT-in-the-browser behaves unlike a known-good native OCCT);
- a **regression** (something that used to be right no longer is);
- a **mistake in our own measurement/oracle code** (see the worked example below — this is a real category, not a hypothetical).

This scoping is deliberate and it *simplifies* the harness. The prior spec's claim that golden values "certify the geometry is actually right, because they come from an independent kernel" is **withdrawn**: `pythonocc-core`, `cadquery-ocp` and our WASM build are all bindings to **the same OCCT C++ code** — a different *build*, not a different *kernel*. That claim was never true, and pursuing it was never the goal.

### 9.1 The harness

Every BIM Object Type's `buildGeometry` is gated in CI **against the WASM build only** — the OCCT-native Python oracle is **never** run in CI.

Every check runs against **both** the real kernel and the protocol-conformant mock, through the protocol, so the two cannot drift apart.

1. **Reference-build oracle (primary).** Gross **volume / area / length** and **solid / face / edge counts** are seeded **offline** from a **native OCCT build** (`cadquery-ocp`) on a **pinned environment** (Section 6.5), then committed. They are compared against the kernel's **`measure` op** (D17) — exact values from **`BRepGProp`**, *never* derived from the mesh. Because the reference runs the same kernel through a *different binding, a different build and a different code path*, a disagreement means **our WASM build or our wiring is wrong** — which is exactly what we are trying to catch. It cannot, and is not asked to, certify OCCT itself.
   > **Why `measure` must exist (D17).** Measuring the *tessellation* is exact only for **planar-faced** solids. A tessellated cylinder under-reports its volume by the chord error — so a circular Column could not be gated at all, and any quantity schedule built on the mesh would quietly under-bill every column in the project. **Quantities come from the B-Rep, which is the source of truth; the mesh is a disposable projection** (Section 1).
2. **Mesh-fidelity check (planar cases).** The same quantities are **re-derived from the triangles** and required to reproduce the exact values. This is a genuinely *independent* second view: a mesh that is mis-wound, not watertight, or missing a face still yields a **perfect `measure` result**, because `measure` reads the B-Rep and never looks at the mesh. This is the only check that can see the *mesh itself* is wrong. Applies to planar-faced solids only — a curved solid legitimately fails it, which is precisely why `measure`, not this, is the gate.
3. **Closed-form sanity check (where a formula exists).** For shapes with an exact closed form — boxes, extrusions of polygonal profiles, cylinders, and a box-minus-box opening, i.e. essentially every v1.0.0 MVP shape — the analytic value is computed and cross-checked **at seed time**, and the seeder **aborts** on disagreement. Cheap (arithmetic, no kernel), and it guards the layer the reference-build oracle cannot: **our own measurement and seeding code.** Not required where no closed form exists (a fillet on a boolean edge); there, tier 1 stands alone, which is acceptable under §9.0.
4. **Regression snapshots (no-regression only).** **Per-sub-shape mass checksums** (over the naming engine's token map) and the **adjacency-graph hash** (topology graph, nodes labelled by structural `SubShapeRef` IDs, canonically serialized, SHA-256) are **self-snapshotted from Bunyan's own engine** — no external tool can produce structural-ID labels. They guard against *drift*, and certify nothing on their own.
5. **Bounds.** Each feature's **tight** `Bnd_Box` is checked against an explicit bounds schema. ⚠ **OCCT's bounding box is *tolerant*, not tight:** `BRepBndLib::Add` enlarges it by the shape's tolerance, so a box sitting exactly on the origin reports `xMin = −1e-7`. The gap must be cleared (`Bnd_Box::SetGap(0)`) to get the tight box the schema means.
6. **⚠ Naming honesty (new 2026-07-12).** The harness **re-measures the role labels** the kernel assigns: a face named `x-min` must actually *be* the face at minimum x. See the §4.5 hazard — a first implementation mislabelled four of a box's six faces while **every numeric check still passed**. Nothing else in the harness can see this class of bug, because the geometry is perfect and only the *names* are wrong.
7. **WASM-heap leak canary.** After a rebuild cycle, the registry's live-handle count is asserted against the **WASM module's own independent count** (spec §6.2). A registry agreeing with itself proves nothing.

The harness also asserts **`SubShapeRef` resolution stability** across parameter changes, and that **the mock and the real kernel emit identical refs** for the same input — the property that makes the mock→kernel swap a no-op for the browser (Section 12).

> **Worked example — why the closed-form tier is retained (2026-07-11, found on its first run).** The closed form said a 3000×200×2500 mm box has **22,800 mm** of edges; OCCT's `BRepGProp::LinearProperties` on the solid said **45,600 mm** — exactly double, because it sums each edge once per adjoining face and every edge of a closed solid touches two. This was **our misuse of the OCCT API**, not an OCCT defect. Without the closed-form check, 45,600 mm would have been committed as the trusted golden, and a *correct* future implementation would have failed CI against it. Fixed by measuring over deduplicated edges.
>
> **This is now a pattern, not an anecdote.** Building the real kernel (2026-07-12) produced **two more of exactly the same shape**: the mislabelled box faces (§4.5) and the tolerant bounding box (tier 5 above). **Every bug this harness has ever caught has been our misreading of an OCCT API — never an OCCT defect.** That is the strongest possible evidence for the §9.0 scoping, and the reason these tiers are not negotiable.

- **Golden seeding + re-seed rule.** Golden values are generated **once, offline**, from `cadquery-ocp` on a **pinned environment** (Section 6.5), then committed. **A new or changed `buildGeometry` MUST ship with re-seeded goldens — CI fails a build that adds geometry without them.** This gate is explicit, and enforced by a machine check, so headless agents don't miss it.
- **Persistent-naming regression suite.** A dedicated corpus of "edit host, verify dependents re-resolve or correctly break" scenarios — the highest-risk subsystem, and the **gate that validates OCCT edge/vertex history coverage** (Section 4.5). This same corpus is the **reference-stability corpus** replayed by the **kernel-migration gate**: a build that upgrades OCCT within the 1.0.x line fails if any reference re-resolves differently.
- **IFC import-fidelity corpus (export deferred).** A growing library of `.ifc` sample files plus Bunyan-authored `.bimproj` files, run through **import + mapped-or-GenericSolid** fidelity checks on every CI build. ⚠ **Fidelity here means *solids*, not pictures** (decision D16): an imported element must be measurable, sectionable and booleanable — so the corpus asserts volume/area against the source, not just that something rendered. **Full IFC export round-trip is a v1.0.x gate**, not v1.0.0 (decision D3).
- **Command-level unit tests.** Every Command in the registry (Section 4.2) has isolated tests against a mock `DocumentContext`, independent of the UI, including a **failure-path test** (Section 6.4).
- **Operation-failure tests.** Known-failing operations (over-large fillet, open profile, empty boolean) must surface a typed failure and leave the document at last-good state — no crash, no partial edit.
- **Import hardening tests.** Malformed / hostile `.bimproj` (zip) and IFC inputs — decompression size/ratio caps, entry-count limits, schema validation, worker-timeout parsing — must fail safe without hanging or OOM-ing the tab. The `geometry-cache.brep` deserialization path is treated as untrusted input on load.
- **Visual regression** against both WebGPU and WebGL2 backends (from the first phase that produces pixels — resolves O5).
- **First-load budget check** (Section 8) runs in CI on a throttled profile and blocks release on regression.

## 11. Licensing — **Bunyan is open source** *(decision D15, owner ruling 2026-07-12)*

> **⚠ THIS SECTION IS FULLY REWRITTEN.** It previously said *"do not build on AGPL-3.0-licensed frameworks"* and treated licensing as a pre-release compliance chore. **Bunyan is now itself AGPL-3.0.** The old guidance is withdrawn.

**The licence: AGPL-3.0, dual-licensed with a commercial option.** The source is public; anyone may use, study and fork it. A **commercial licence** is sold to those who need to stay closed. (Grafana / Mattermost model.)

**Why AGPL and not GPL.** AGPL closes the **SaaS loophole**. Under plain GPL, a rival could take Bunyan, improve it, and run it as a **hosted service** without publishing a line. AGPL compels them to publish. **The moat was never the client code — it is hosted collaboration**, and AGPL is the licence that defends precisely that.

**Why open source at all (the strategic reasoning, recorded so it is not re-litigated).** We cannot out-feature Revit — Autodesk has 30 years, thousands of engineers, and a content ecosystem. **We win where Revit is hated:** lock-in, subscription pricing, an opaque format, a heavy Windows install. Browser-native + IFC-native + no-install is the wedge — and **openness is not a footnote to that wedge, it *is* the wedge** ("you will never lose access to your models, and you can verify what the geometry engine does"). It also buys the one thing a small team cannot build alone: an **ecosystem** (content, plugins, national standards). AEC already has a strong open-source culture — IFC itself, and IfcOpenShell, which we now depend on.

**Dependency compatibility — verified, not assumed:**

| Dependency | Licence | Compatible? |
|---|---|---|
| **OCCT** (statically linked into our `.wasm`) | **LGPL-2.1** | ✅ **Yes.** LGPL-2.1 **§3** expressly permits converting a copy of the library to the ordinary GPL, and states that if a GPL newer than v2 exists, *"you can specify that version instead."* ⇒ OCCT composes with AGPL-3.0. |
| **IfcOpenShell** (D16) | **LGPL** | ✅ Same reasoning. |
| three.js, React, Vite, … | MIT / permissive | ✅ |

**⚠ The static link STANDS — and this is why it matters.** LGPL-2.1's *relink obligation* exists so that a user can rebuild the app against their own modified OCCT. **Public, buildable source satisfies that automatically** (clone the repo, rebuild). ⇒ **Do not build an OCCT side-module, and do not ship object files.** *(An earlier ruling mandated a swappable side-module; it assumed Bunyan would be proprietary and is superseded. It would have cost most of the 9× size advantage of D14, since a swappable module cannot be dead-stripped.)*

**⚠ LGPL still requires prominent attribution** that the product uses OCCT (and IfcOpenShell). This goes in the README **and** the app's About screen. **Not optional.**

**⚠ THE CLA IS A HARD PREREQUISITE, AND IT IS EASY TO GET WRONG BY WAITING.** Dual-licensing only works if the owner holds the rights to **every line**. The moment an external contribution is merged **without a signed CLA**, that contributor holds copyright on it and it can **never** be included in a commercial licence without their permission. **⇒ The CLA (contributors grant the owner a licence including the right to relicense commercially) MUST be in place BEFORE the first external pull request.** A **DCO will not do** — it certifies authorship but grants **no relicensing right**, which would foreclose the business model entirely.

**Timing.** The repo goes **public later, at a milestone** (working geometry + editor) — not immediately. Until then it stays private. **Before it goes public**, the following must land (none of it blocks kernel work): `LICENSE` (AGPL-3.0) · the **CLA** · AGPL file headers · the **OCCT + IfcOpenShell attribution notice** · a `NOTICE` / third-party licence section.

**A bonus that follows from going public:** public GitHub repos get **unlimited Actions minutes** and the **4-vCPU / 16 GB** runners (private repos get 2 vCPU / 7 GB on 2,000 min/month). This retires the "never iterate a build recipe in CI" constraint — **but only once the repo is actually public.**

The 2026-07-08 "independent kernel / first-correctness" framing is **withdrawn** — `pythonocc-core`/`cadquery-ocp` and our WASM build are the **same OCCT**, so it was never independent, and validating OCCT is explicitly **out of scope**. The harness is: (1) **reference-build oracle** — volume/area/length + topology counts from a **native OCCT build** (`cadquery-ocp`), which catches *our* build/wiring errors; (2) **closed-form sanity check** at seed time where a formula exists, guarding *our own measurement code* (it caught a real defect on its first run — see the §9.1 worked example), not required where no closed form exists; (3) **regression snapshots** (mass-checksum + adjacency-hash, Bunyan-only, drift-only); (4) bounds. |
| **D10** | OCCT operation-failure behavior? *(2026-07-08)* | **Reject + keep last-good**, marshal `Standard_Failure` safely as a typed failure (Section 6.4). Auto-repair + repro-bundle flagged for **v1.0.x**. |
| **D11** | Offline capability? *(2026-07-08)* | **Service worker + PWA** precache app + versioned WASM (Section 8), backing the Section 1 offline principle. In v1.0.0 scope. |
| **D12** | Opening behavior on host resize? *(2026-07-08)* | **Per-opening anchoring parameter** — `fixed` (default) / `proportional` / `centered` (Section 5.1; `core_logic.md`). |
| **D13** | Contract-freeze timing? *(2026-07-08)* | **Split freeze** (Section 12): protocol frozen at P3; `BimObjectType`/`Command`/`SubShapeRef` release-candidate until Wall+Opening validate them in P5. **⚠⚠ OPEN — AND IT MUST BE SETTLED BEFORE P3 ENDS (audit, 2026-07-13, Entry 13): WHAT DOES "FROZEN" ACTUALLY FORBID?** As written, it forbids everything — **and that forecloses P6, which nobody noticed for 12 entries.** P6 **needs a `sectionCut` op** (the 2D plan + elevation: a headline v1.0.0 deliverable and the *proof* that the kernel is the source of truth) **and IFC-import ops** (D16 — IfcOpenShell exposed as new C++ ops, by construction). **Neither exists; neither is scheduled before the freeze.** ⇒ **P6 would open by amending a frozen contract, which makes the freeze theatre.** Two ways out, and the Architect owns the call: **(a)** *reserve the op shapes* before the freeze — typed stubs suffice, because **the payload shape is the expensive thing to change, not the body**; or **(b)** **re-word the freeze** as *"ADDING a new op is additive and permitted; CHANGING an existing op's envelope or payload needs Architect sign-off"* — which is very likely what was always meant, **but is not what this row says.** An unstated intent is exactly what a freeze exists to eliminate. |
| **D14** | Which OCCT→WASM kernel? *(**2026-07-12, owner ruling**)* | **Build upstream OCCT 7.9.3 ourselves** (`tools/kernel-build/`), and **statically link it with our own C++ op set**. **`opencascade.js` is rejected**, on four independent grounds: (1) it **cannot be linked on the build box at all** — its `-flto` object cache forces a whole-program-optimisation link that is OOM-killed even for a *6-symbol* build (proven, not assumed); (2) it is **dormant since March 2023** (OCCT 7.6.2, emscripten pinned at 2022); (3) it exposes **all of OCCT to JavaScript** (8,975 binding objects), which is why it ships 62.8 MB and pays **a boundary crossing per OCCT call**; (4) **it forecloses linking a second C++ library — i.e. IfcOpenShell (D16)**, which is the only route to exact IFC solids. Our build: LTO **off**, **modelling toolkits only** (Visualization/OCAF/DataExchange/Draw dropped), **3.98 MB / 1.47 MB gzip**. **The product grows by writing more C++ ops, not by growing the JS binding surface.** |
| **D15** | Licence & openness? *(**2026-07-12, owner ruling — the biggest of the project**)* | **BUNYAN IS OPEN SOURCE: AGPL-3.0, dual-licensed with a commercial option.** AGPL (not GPL) because it closes the **SaaS loophole** — the moat is *hosted collaboration*, not the client code. **Openness is the wedge against Revit**, not a footnote to it. Compatibility with OCCT/IfcOpenShell (both LGPL) **verified** via LGPL-2.1 §3. **⇒ The static link stands and the OCCT side-module is CANCELLED** (public buildable source discharges LGPL's relink obligation automatically). **⚠ A CLA — not a DCO — must be in place BEFORE the first external PR**, or the commercial licence is foreclosed forever. Repo goes public **at a milestone**, not now. Full reasoning: Section 11. |
| **D16** | IFC import: triangles or solids? *(**2026-07-12, owner ruling**)* | **EXACT B-REP SOLIDS, via IfcOpenShell.** **`web-ifc` is rejected** — it returns **triangles**, which cannot be measured, sectioned, booleaned or parametrically edited. An imported model would be a *backdrop*, not a building, and it would **break the core invariant** that B-Rep is the source of truth (Section 1). IfcOpenShell is C++ and **must link against *our* OCCT build** — possible **only because of D14**. ⇒ **Never adopt a kernel path that forecloses linking a second C++ library.** |
| **D17** | How are quantities measured? *(**2026-07-12, owner-approved**)* | **A `measure` op in the protocol**, backed by OCCT's **`BRepGProp`** — exact volume/area/edge-length + topology counts, **never derived from the mesh**. Measuring a tessellation is exact only for **planar-faced** solids; a tessellated cylinder under-reports its volume by the chord error, so a circular Column could not be gated and every column in a schedule would be under-billed. **Quantities come from the B-Rep; the mesh is a disposable projection.** Added before the P3 protocol freeze, as required. |
| **D18** | Where does sub-shape identity get assigned — C++ or TS? *(**2026-07-12**)* | **Both, split by question.** **C++ assigns ROLES** (*"which sub-shape is this, structurally?"*) — from each operation's own semantic accessors, and from topology for edges. **TS assigns IDENTITY** (*"whose is it?"*) — binding roles to the owning DAG node and encoding the `SubShapeRef` token. Geometry enters neither half. The kernel **refuses to name** what it cannot derive structurally rather than inventing an identity (Section 4.5). |
| **D19** | How does an AI agent operate Bunyan? *(**2026-07-12, owner ruling — the architectural one**)* | **ONE COMMAND LAYER FOR EVERY ACTOR. There is no second API, and no actor bypasses it.** Humans and agents act on the document through **the same Commands** (Section 4.6.1); **`DocumentContext` is the only holder of a `KernelClient`** — no React component and no agent may call a kernel op directly. *Why "no exceptions":* every capability reachable **only** through the UI is a capability the agent can **never** have, and the gap is invisible until an agent is asked to use it. **If the UI can do it, a Command expresses it; if no Command expresses it, the UI cannot do it.** ⚠ **Two layers exist and only one is the agent's:** kernel ops (`makeBox`/`tessellate`, frozen at P3) are an *implementation*, not an API; document commands (`createElement`/`setProperty`, frozen at P5) are the API. An agent calling a kernel op would create a solid **no entity owns, no undo can remove, and no `SubShapeRef` names.** **Promoted to a north-star in `core_logic.md` §9 and a guiding principle in §1** — so no future decision may foreclose it. |
| **D20** | Command granularity for agents? *(**2026-07-12, owner ruling**)* | **TYPE-DRIVEN VERBS by default; primitives are the escape hatch.** The primary verb is **`createElement(typeId, params)`** — *"create a `core.wall.v1`, 4000 mm long"* — not *"draw a rectangle, then extrude it"*. **This is free:** a BIM Object Type already *is* the recipe from parameters to geometry (§4.1), so the parametric registry makes semantic verbs the natural default. Sketch-level primitives (§5.2) remain as the **GenericSolid** escape hatch. **Composite verbs** ("add a room") are **v1.0.x** — they need transaction grouping (D23), for which the contract now reserves room. |
| **D21** | Where does the agent's capability/schema description live? *(**2026-07-12, owner ruling**)* | **GENERATED FROM THE REGISTRIES. Never hand-maintained.** `Command` gains an **`argsSchema`**, exactly as `BimObjectType` already carries a `parameterSchema`. The registries are already the **only** place a type or command can be declared (§4), so a generated schema **cannot drift**; a hand-written agent document certainly would, within weeks. **One registry, three consumers:** `contributesUI` → the ribbon, `parameterSchema` → the property panel, `argsSchema` → **the agent's tool list**. A new command becomes an agent verb **with no way to forget**. ⇒ **An agent needs no external documentation: it asks the app.** |
| **D22** | Agent transport — `window.*` or MCP? *(**2026-07-12, owner ruling**)* | **`window.bunyan` FIRST (zero install). MCP DEFERRED to v1.0.x — not rejected.** *"No complex setup" is a hard requirement, and an MCP bridge **is** that setup* — a download, a config file, and a local process — which would also puncture the property that defines v1.0.0: **client-only, zero backend, designs never leave the device** (§1). `window.bunyan` ships **with the app** and serves an in-browser agent (e.g. Claude in Chrome) with no SDK. **MCP stays cheap precisely because of D19: it is another *transport* over the same verb set, not a second API** (the same move the kernel's swappable `Transport` already proves). **The surface is versioned separately** (`agentApi`), independent of `protocolVersion` and of the P5 type-contract freeze, so agent ergonomics can improve **without amending a frozen contract**. ⚠ It is a **page-global** API — fine in v1.0.0 (no backend/account/secret), but a real trust boundary the moment the page runs code we did not author (**the Pyodide macro console**); that capability grant is decided **before** that code ships. |
| **D23** | How does an agent explore state and verify its own work? *(**2026-07-12, owner ruling**)* | **EXPLORE → ACT → VERIFY, all through the same layer.** (1) **Read/query in two tiers:** document-level queries (`getSceneGraph`/`getElementById`/filter) read the **parametric recipe**, which *is* the truth — **no kernel op needed**; geometric queries (tight bounds, spatial proximity) need the B-Rep and are **kernel ops added BEFORE the protocol freezes at the end of P3** (one line in `OpMap` now; a contract amendment later). (2) ⚠ **Queries return SEMANTICS, not triangles** — a `Float32Array` is unreadable to an agent; the agent reads a semantic **Representation** (§4.4). *The 3D view is the projection for eyes; this is the projection for reasoning — both derived, neither truth.* (3) **Every command RETURNS its `UndoableEdit`** — the delta undo needs to reverse an action and the diff an actor needs to verify it are **the same object**, so with the exact **`measure`** op (D17) and typed failures (§6.4) the agent has a **closed loop: act → read the diff → measure the result.** (4) **Transaction grouping is RESERVED** in `UndoableEdit` (not built): v1.0.0 emits one edit per command, but the field is fixed now because the undo contract freezes at P5 and every composite verb will need it. (5) ⚠ **Agent commands opt OUT of edit-coalescing** — `SUPERSEDED` is meaningless to an agent that issued one deliberate command; **coalescing is a property of interactive input, not of commands.** |
| **D24** | Does OCCT's history actually support persistent naming on hard topology? *(**2026-07-12, MEASURED — not a ruling; the numbers decided it**)* | **YES — and the received wisdom was wrong about WHERE it is weak.** §4.5 previously repeated the OCCT-docs/FreeCAD claim that history is *"weakest for edges and vertices from boolean section curves"*. We **measured** it on OCCT 7.9.3 instead (`tools/kernel-build/probe.cpp`, committed, ~60 s to re-run). **Boolean history is COMPLETE — zero orphans** across a window cut, a circular penetration and a corner fuse; section edges come back in `Generated()` of **both** intersecting faces. **The weak spot is the FILLET**, which rebuilds the edges/vertices *around* what it touches with no history at all. **The relation everyone misses is IDENTITY:** `Modified()` reports only *splits*, so an untouched face is passed through in silence — read as *"unknown"* rather than *"unchanged"*, it makes history look far worse than it is (4 of a wall's 6 faces, on a simple cut). ⇒ **The resolver is four relations — PRIMITIVE / INHERIT / DERIVE / ADJACENT** (§4.5) — and on the spec's designated hardest case (**a fillet on a boolean-made edge**) it names **everything, with no geometric fallback**. **The sanctioned positional key is therefore NOT implemented**: nothing has needed it, and an untested geometric rule on the identity path is a liability, so the resolver **refuses** instead. ⚠ **A cylinder's SEAM — not the boolean — was the first wall**: bounded by one face twice, it has no face *pair*, and the old kernel refused to build a cylinder at all. |
| **D25** | Which geometric query ops ship, and what may they return? *(**2026-07-12** — the D23 mandate, made concrete before the P3 freeze)* | **THREE OPS: `bounds`, `distance`, `classifyPoint`.** `bounds` answers for a whole shape **or for one NAMED sub-shape** (*"where exactly is the south face of that wall?"* — a question only persistent naming makes askable). `distance` returns the minimum separation **plus the two witness points**, so **zero doubles as the clash primitive**. `classifyPoint` returns `inside` / `outside` / **`on`** — the boundary is its own answer, because a wall's surface is exactly where things get hosted. ⚠ **They read the B-REP, never the mesh, and they return millimetres and identities — never triangles.** A tessellated column is *smaller* than the real one by its chord error, so an agent reasoning about clearances from the mesh would confidently under-report every clash in the project. **Implemented in BOTH kernels** — the mock answers them in closed form for a box, so the agent/query path is buildable without the 14 MB wasm. **Placement (`at`) was added to the primitives in the same pass**: without it both solids sit at the origin and a boolean can only bite a **corner** off a wall — a window in the middle, the one operation this product exists to perform, was unreachable. |
| **D26** | How is a Slab, a Column or a GenericSolid actually built — and what names its faces? *(**2026-07-13**, Entry 12 — found by MODELLING A BUILDING, not by reading the protocol)* | **AN `extrude` OP OVER AN AUTHORED PROFILE, plus `chamfer`. Both were in P2 step 1's scope and neither was ever built** — and nothing noticed, because no test had tried to build a floor plate. **`makeBox` cannot express three of the five MVP types** (§5): a **Slab** is *"planar boundary + thickness"*, and a real plate is L-shaped, five-sided, or has a curved edge; a **Column** may have an arbitrary profile; and **GenericSolid** (*"free sketch + extrude/revolve"*) — the escape hatch and the unmapped-IFC import target — has no op behind it at all. **The profile is a closed loop of AUTHORED segments** (line, or a **three-point arc** — three points define exactly one arc, so there is no handedness flag to get backwards and no radius too small for its chord). It is validated **closed and non-self-intersecting** before it reaches a solid op (§5.2), returning a typed **`INVALID_PROFILE`** — a figure-eight boundary is closed and planar and still nonsense. **⚠ THE NAMING RULE, AND IT IS A CONTRACT, NOT AN IMPLEMENTATION DETAIL: the face swept from segment `k` is named `lateral.k`, where `k` is the index in the array THE AUTHOR DREW** — never OCCT's traversal of the wire. That is what lets a user **drag a slab's corner** — moving the boundary and changing every coordinate of two faces — **without re-targeting a single reference into it.** Consequently **reordering the segment array re-targets every reference into the shape**, exactly as renaming a wall would: editing a vertex is safe, permuting the list is not, and a document command must never do it silently. **`chamfer` is the fillet's flat sibling** — same contract (the edge is addressed **by identity**), same resolver, same weak spot. ✅ **`revolve` landed in Entry 14 (D27) — the op set of P2 step 1 is now complete.** |
| **D27** | How is a REVOLVE named — and is it just the prism with a rotation? *(**2026-07-13**, Entry 14 — MEASURED with the probe before a line of the resolver was written)* | **NO. Copying the prism would have shipped a kernel that REFUSES EVERY FULL REVOLVE.** `revolve` completes GenericSolid (*"free sketch + extrude/**revolve**"*, §5) and the P2 step 1 op set, and it carries **the same naming contract as `extrude` (D26): `lateral.k` after the AUTHORED segment**, so re-authoring a column's profile re-targets nothing. But a **full 360° turn is not a partial one with a bigger number**, and all three differences were measured, not guessed (`probe.cpp` cases 12-15, ~60 s to re-run): **(1) it has NO CAPS** — and OCCT's `FirstShape()`/`LastShape()` do **not** return null for it, they return a face **that is not in the result**, so the test is *"is it in the result"*, never *"is it null"*; **(2) every lateral face has a SEAM** (it closes on itself, so no face *pair* bounds the seam edge — the cylinder's problem), but unlike the cylinder **the seam IS the authored profile edge**, returned by *identity*, so it costs nothing: `lateral.k.seam`; **(3) ⚠ a segment PERPENDICULAR to the axis generates NO HISTORY AT ALL** — `Generated()` empty, `IsDeleted()` true — **while its face is right there in the result.** That face is the flat bottom of every column and the base of every dome. It is named from **the circles swept by its segment's own endpoint vertices** — pure topology — and the same relation tells it apart from a segment lying **on** the axis, which sweeps no circle and correctly has no face at all. **Gated by four goldens** (a column that must measure identically to the `makeCylinder` primitive; a hollow tube, whose annuli are the history-less faces; a hemisphere from an arc, whose closed form is 2/3·π·r³; and a 90° control that HAS caps), each checked against **native OCCT and an independent closed form**. |
